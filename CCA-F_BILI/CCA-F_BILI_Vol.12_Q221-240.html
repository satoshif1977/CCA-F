Q221Claude Code — Entry Point Selection
🇯🇵 Japanese
小売銀行ワークフローの提案が、支店スタッフ向けに Claude Code を使用することを「根底にあるのはすべて Claude だから」という理由で提案している。支店スタッフはエンジニアではなく固定業務フローに従う。この提案に含まれる設計上の誤りは？
✓ 正解
エントリポイントはユーザーと業務内容を考慮した上で選ぶべき決定である。Claude Code は開発者向けに作られたエンジニアリングエントリポイントであり、支店スタッフが業務フローに従うのに適していない
💡 暗記ポイント
エントリポイント・ビルド時インターフェース・デリバリルートは3つの独立した決定。「根底は同じモデル」はこれらの層を混同した誤り。Claude Code は開発者・ターミナル向けのエンジニアリングツール。ユーザーと業務内容が合わないエントリポイントは UX 障壁を生む。
🇺🇸 English
A proposal for a retail banking workflow puts Claude Code in front of branch staff on the grounds that "it's all Claude underneath." Branch staff are not engineers and will follow a fixed operational workflow. What architectural error does the proposal contain?
✓ Correct Answer
The entry point was chosen before the user and the work were considered; entry points, build-time interfaces, and delivery routes are distinct decisions.
🔑 Key Words
entry pointエントリポイントユーザーが Claude にアクセスする窓口・インターフェース
Claude CodeClaude Code開発者向けターミナルツール（エンジニアリングエントリポイント）
build-time interfaceビルド時インターフェースアプリ設計時に選ぶ Claude との統合インターフェース
delivery routeデリバリルートClaude 機能をユーザーに届ける流通経路
Q222Agent Architecture — Workflow Routing Pattern
🇯🇵 Japanese
受信サポートチケットには種類のばらつきがある：請求質問はアカウントデータへの取得が必要、技術的問題は製品ドキュメントへの取得が必要、エスカレーションは直接人間キューへ。このシェイプに最も適したワークフローサブパターンは？
✓ 正解
ルーティング。分類器が各チケットを読み、下流のパスを選択するため
💡 暗記ポイント
入力の種類が異なり処理が分岐する → ルーティング。チェーン（固定順序で同じステップを順に実行）・並列化（すべてのパスが同時実行）・Evaluator-Optimizer（出力品質の改善ループ）は異なるパターン。ルーティングは最初に分類してから適切な下流処理に振り分ける。
🇺🇸 English
Incoming support tickets vary in kind: billing questions need retrieval over account data, technical issues need retrieval over product documentation, and escalations must go straight to a human queue. Which workflow sub-pattern fits this shape?
✓ Correct Answer
Routing, because a classifier decides which downstream path each ticket takes.
🔑 Key Words
routingルーティング入力の種類を分類して適切な下流パスに振り分けるパターン
chainingチェーン固定したステップを順番に実行するパターン
parallelization並列化独立したサブタスクを同時並行で実行するパターン
evaluator-optimizer評価・最適化ループ一方のモデルが出力し他方が改善を指示する品質改善パターン
Q223Claude Code — Skill Packaging
🇯🇵 Japanese
複数の異なるワークフローが同一に実行する必要のある繰り返し可能な多段階レポートフォーマット手順があり、一箇所でバージョン管理・更新される必要がある。このジョブに一致するプリミティブは？
✓ 正解
スキル。繰り返し可能な手順をバージョン管理された再利用可能なユニットとしてパッケージ化するため
💡 暗記ポイント
繰り返し可能な手順 + バージョン管理 + 複数ワークフローからの再利用 = スキル。ツールはアクション・ルックアップを公開する。サブエージェントはスコープを隔離・並列化する。MCP はツールを複数クライアントに公開するプロトコル（仕組み）であり手順をパッケージ化しない。
🇺🇸 English
A team has a repeatable, multi-step report-formatting procedure that several different workflows must execute identically, and the procedure needs to be versioned and updated in one place. Which primitive matches this job?
✓ Correct Answer
A Skill, because it packages a repeatable procedure as a versioned, reusable unit.
🔑 Key Words
Skillスキル繰り返し可能な手順をバージョン管理された再利用可能ユニットにするプリミティブ
versionedバージョン管理された変更履歴を追跡し特定バージョンに戻せる状態
reusable再利用可能複数のワークフロー・プロジェクトから利用できる
primitiveプリミティブClaude エコシステムの基本構成要素（ツール・スキル・サブエージェント等）
Q224Solution Design — Decomposition & Comparative Advantage
🇯🇵 Japanese
分解中、アーキテクトがパートナーのプロセスの各ステップを列挙し「Claude はどこで役立てるか？」と問い、既存のルールエンジンがすでに正しく実行している複数のステップを含めて大半のステップを Claude に割り当てた。アーキテクトが使うべきだった正しいフレーミングは？
✓ 正解
「4つの特性が、すでに正しく実行しているシステムより Claude に有利に働く場所はどこか？」— 比較優位で所有者を割り当てる
💡 暗記ポイント
Claude の所有権は比較優位で決定する。「どこで Claude が役立つか？」は Claude の過剰割り当て（最も一般的で高コストな初期ミス）を生む問い方。ボリューム（頻度）・プロトタイピング速度・人気度はいずれも所有権の基準ではない。すでに正しく動いているシステムより Claude が有利な場所だけに割り当てる。
🇺🇸 English
During decomposition, an architect lists every step of a partner's process and asks, "Where can Claude help?"—then assigns most steps to Claude, including several a rules engine already performs correctly. What is the correct framing the architect should have used?
✓ Correct Answer
"Where do the four properties argue for Claude over the system that already does this right?"—assigning owners by comparative advantage.
🔑 Key Words
decomposition分解プロセスをステップに分割し所有者を割り当てる作業
four properties4つの特性Claude が比較優位を持つ能力特性（柔軟性・自然言語・推論等）
comparative advantage比較優位他システムより Claude がより優れている点で判断
over-assignment過剰割り当て不要なステップまで Claude に割り当ててしまうミス
Q225Prompt Engineering — Few-shot for Format Fidelity
🇯🇵 Japanese
抽出タスクが独自のハウスフォーマットで出力する必要がある。詳細な文書指示だけでは実行間でフォーマットが小さく多様な形でドリフトする。このフォーマットドリフトに最も直接的に対処するプロンプトエンジニアリングの変更は？
✓ 正解
正確なターゲットフォーマットを示す few-shot 例を指示と一緒に追加する
💡 暗記ポイント
独自フォーマット + 指示だけでドリフト = few-shot 例の追加が答え。フォーマットが独自（idiosyncratic）な場合、説明より例示が有効。ステアラビリティの限界として、短くて具体的な指示 + 例示が最強の組み合わせ。温度を上げると分散が増加（逆効果）。
🇺🇸 English
An extraction task must produce output in an idiosyncratic house format. Detailed written instructions alone produce output that drifts from the format in small, varied ways across runs. Which prompt-engineering change most directly addresses this?
✓ Correct Answer
Add few-shot examples demonstrating the exact target format alongside the instructions.
🔑 Key Words
few-shotフューショット手本を数例示して出力パターンを誘導する手法
format fidelityフォーマット忠実性指定フォーマットへの準拠度・一貫性
idiosyncratic独自の・固有の一般的でない特殊なフォーマット・規則
steerabilityステアラビリティプロンプトで Claude の出力を誘導できる性質
Q226Prompt Engineering — Intent vs Letter
🇯🇵 Japanese
システムプロンプトが「100語以内に回答を収めよ」と指示している。モデルはルールの文言には従うが、制限内に収めるために法的に必要な開示テキストを省略し、指示の意図からドリフトしている。この失敗モードに対処する設計変更は？
✓ 正解
指示の目標を明示的に再記述し（例：必要な開示は常に簡潔さより優先されること）、必要なテキストを構造化出力チェックで強制する
💡 暗記ポイント
ルールの文言に従って意図を外す（文言 vs 意図のドリフト）は既知のステアラビリティ限界。対策は目標の明示化（「開示 > 簡潔さ」）+ 非交渉可能コンテンツの決定論的検証（構造化出力チェック）。制限削除（要件自体を捨てる）や繰り返し（競合を解消しない）では解決しない。
🇺🇸 English
A system prompt instructs an assistant to "keep responses under 100 words." The model complies with the letter of the rule but omits legally required disclosure text to stay under the limit. Which design change addresses this failure mode?
✓ Correct Answer
Restate the goal explicitly alongside the instruction—for example, that required disclosures always take precedence over brevity—and enforce the required text with a structured output check.
🔑 Key Words
intent vs letter意図 vs 文言ルールの文字通りに従って本来の意図を外すドリフト
structured output構造化出力スキーマで出力フォーマット・必須要素を強制する手法
non-negotiable content非交渉可能コンテンツ必ず出力しなければならない必須テキスト
disclosure開示法律・規制が要求する必須の情報公開テキスト
Q227Integration & Reliability — Retry Strategy
🇯🇵 Japanese
デプロイメントが本番環境で断続的に 429（レートリミット）と 529（過負荷）レスポンスを受け取る。現在のクライアントコードは各失敗呼び出しをタイトなループで即時リトライしており、これがインシデントを長引かせる。正しい信頼性設計を反映した変更は？
✓ 正解
指数バックオフと上限回数でリトライし、一時的なヒッカップが長引く停止に増幅されないようにする
💡 暗記ポイント
429・5xx は一時的なエラー。正しい制御は指数バックオフ + キャップされた試行回数。タイトなループリトライはレートリミットを悪化させインシデントを長引かせる（負のフィードバックループ）。リトライなしはUX劣化。別APIキーへの切り替えは制限を回避するだけで問題を解消しない。
🇺🇸 English
Under load, a deployment intermittently receives 429 rate-limit and 529 overloaded responses. The current client code retries each failed call immediately in a tight loop, which prolongs the incidents. Which change reflects correct reliability design?
✓ Correct Answer
Retry with exponential backoff and a capped number of attempts, so brief hiccups are not amplified into prolonged outages.
🔑 Key Words
exponential backoff指数バックオフリトライ間隔を指数的に増やして過負荷を防ぐ
rate limit (429)レートリミット (429)APIリクエスト数の上限超過を示すHTTPステータス
retry strategyリトライ戦略失敗したリクエストを再試行する方法・回数の設計
tight loop retryタイトループリトライ間隔なしに即時リトライを繰り返す（問題のあるパターン）
Q228Agent Architecture — Trajectory Control
🇯🇵 Japanese
広いツールセットを持つエージェントが非常に長いトラジェクトリを実行することがある：ツール呼び出しが繰り返され、コンテキストが膨らみ、誰も気づかないうちに 1 つのリクエストがコストシーリングを超える可能性がある。このアーキテクチャの特徴的な失敗モードに対処する設定変更は？
✓ 正解
ターンごとのトークン予算・最大ツール呼び出し回数・明示的な停止基準を設定し、出力品質だけでなくエージェントの停止動作も評価する
💡 暗記ポイント
エージェントの特徴的な失敗：無制限のツール使用 + コンテキスト膨張 = コストシーリング超過（サイレント）。対策はターンごとのトークン予算 + ツール呼び出し上限 + 停止基準。停止動作そのものを評価することも重要。大きなウィンドウは症状の上限を上げるだけで根本解決にならない。
🇺🇸 English
An agent with a broad tool set occasionally runs very long trajectories: tool calls repeat, context grows, and a single request can silently exceed the cost ceiling before anyone notices. Which configuration change addresses this architecture's characteristic failure mode?
✓ Correct Answer
Set per-turn token budgets, maximum tool-call counts, and explicit stopping criteria—and evaluate the agent's stopping behavior, not just output quality.
🔑 Key Words
agent trajectoryエージェントトラジェクトリエージェントが実行するツール呼び出し・推論ステップの経路
token budgetトークン予算1ターンあたりに使用できるトークン数の上限
tool-call limitツール呼び出し上限1リクエストで許可するツール呼び出しの最大回数
stopping criteria停止基準エージェントが処理を終了する条件の定義
Q229RAG & Integration — Semantic Chunking
🇯🇵 Japanese
構造的な境界が弱い長文散文のコーパスがある。取得されたチャンクが頻繁にアイデアの途中で切れ、モデルが自己完結していないフラグメントから回答せざるを得ない。このコーパスに適したチャンキング変更は？
✓ 正解
意味の境界で分割し、取得された各チャンクが自己完結するようにする意味的チャンキング
💡 暗記ポイント
弱い構造 + チャンクがアイデアの途中で切れる = 意味的チャンキングが答え。固定サイズ（大きくしても任意の切断は変わらない）・階層的（構造がない文書に不適）・全文書（トークン予算超過・関連性希薄化）はどれも不適。意味の境界で分割するから各チャンクが自己完結する。
🇺🇸 English
A corpus of long-form prose has weak structural boundaries, and retrieved chunks frequently cut off mid-idea, forcing the model to answer from fragments that are not self-contained. Which chunking change fits this corpus?
✓ Correct Answer
Semantic chunking that splits on meaning boundaries so each retrieved chunk is self-contained.
🔑 Key Words
semantic chunking意味的チャンキング意味の区切り（トピック転換）で分割する手法
self-contained chunk自己完結チャンクそれ単体で意味が完結する取得単位
prose散文詩や箇条書きでない通常の文章形式
meaning boundary意味の境界話題・アイデアが切り替わる自然な区切り点
Q230Monitoring — Per-request Instrumentation
🇯🇵 Japanese
RAG デプロイメントのリクエストごとの計装を設計している。将来の品質低下を検出・帰属させられるようにするため、ログに含めるべき2項目を選べ。
※ 2つ選択
✓ 正解
A: グラウンディング文書に対して測定したリクエストのリトリーバル精度（アラート閾値付き）／ B: モデルのバージョンと入出力トークン数（キャッシュヒット/ミスを含む）
💡 暗記ポイント
品質低下の検出・帰属にはリトリーバル精度（取得レイヤーか特定）とモデルバージョン+トークン数（回帰トレース）が必要。エラー数のみでは成功リクエストの品質低下を見逃す。全プロンプトの無期限保持はデータハンドリング・最小化要件に違反する。
🇺🇸 English
A team is designing per-request instrumentation for a RAG deployment before launch, so that a future quality regression can be detected and attributed. Which TWO items belong in the per-request logs?
✓ Correct Answer
A: Retrieval precision for the request, measured against the grounding documents, with an alert threshold. B: Model version and input/output token counts, including cache hit or miss.
🔑 Key Words
retrieval precisionリトリーバル精度取得されたチャンクがグラウンディングに適切か
model versionモデルバージョン使用したモデルの具体的なバージョン識別子
cache hit/missキャッシュヒット/ミスプロンプトキャッシュが有効化されたかどうか
attribution帰属品質低下がどのレイヤーで発生したか特定すること
Q231Governance & Safety — Training vs Inference-time Control
🇯🇵 Japanese
証券会社が「Claude のトレーニングが安全にするため、アシスタントが投機的な投資ヒントを絶対に議論しない」と前提を置いていた。本番環境では制限なく自由に議論し、ポストモーテムでその制限がどこにもエンコードされていなかったことが判明した。このインシデントが示すことは？
✓ 正解
トレーニング時の整合と推論時の制御は2つの異なる目的を持つ別々のレイヤーである。トレーニングは広く有害な動作をカバーし、ビジネス固有のドメインポリシーはオペレーターが推論時の制御レイヤーでエンコードする責任がある
💡 暗記ポイント
「モデルの安全性トレーニングが業務ポリシーも担保する」は誤信。トレーニング時整合は広範な有害性をカバーするが、業務固有ポリシー（投機的投資アドバイス禁止等）はオペレーターがシステムプロンプト・ガードレール等の推論時制御でエンコードする責任がある。どのレイヤーにもエンコードされていないポリシーはどのレイヤーでも適用されない。
🇺🇸 English
A brokerage assumed its assistant would never discuss speculative investment tips because "Claude's training makes it safe." In production, the assistant discussed them freely, and a postmortem found the restriction was never encoded anywhere. What does this incident illustrate?
✓ Correct Answer
Training-time alignment covers broadly harmful behavior; a business-specific domain policy is the operator's responsibility and must be encoded at the inference-time control layer.
🔑 Key Words
training-time alignmentトレーニング時の整合事前トレーニングで組み込まれた広範な安全性
inference-time control推論時の制御システムプロンプト・ガードレール等によるランタイム制御
operator responsibilityオペレーターの責任業務固有のポリシーをエンコードするのはオペレーターの役割
domain policyドメインポリシー特定業種・ユースケース固有のルール・制約
Q232Governance & Safety — Deterministic Authorization
🇯🇵 Japanese
返金発行ツールのために、チームがモデルによる judge で各ツール呼び出しを認可することを提案している。コンテキストを柔軟に考慮できるとの理由で。正しい評価は？
✓ 正解
副作用を伴うアクションの認可は決定論的であるべき — ID とスコープのチェックを持つ許可リストとして。その決定は監査可能かつ再現可能でなければならない。モデルベースのチェックは入力と出力のスクリーニングに属する
💡 暗記ポイント
副作用ツール（返金発行等）の認可はホワイトリスト + ID・スコープ検証で決定論的に行う。モデルベースの認可は確率論的で監査・再現不可（なぜ承認されたか説明できない）。Judge の大きさやログ取得だけでは認可を確実にできない。「いずれかが承認 = 実行」は最も脆弱。
🇺🇸 English
For a refund-issuing tool, a team proposes having a judge model decide whether each tool call should be authorized, reasoning that a model can weigh context flexibly. What is the correct assessment?
✓ Correct Answer
Authorization for side-effecting actions should be deterministic—an allowlist with identity and scope checks—because the decision must be auditable and replayable; model-based checks belong at input and output screening instead.
🔑 Key Words
deterministic authorization決定論的認可ホワイトリスト+ID・スコープ検証による確実な認可
allowlistホワイトリスト・許可リスト明示的に許可されたアクション・主体のリスト
side-effecting action副作用を伴うアクション外部システムに取り消し困難な変更を加える操作
auditability監査可能性決定の根拠を後から追跡・証明できること
Q233Governance & Safety — Fairness & Operator Responsibility
🇯🇵 Japanese
デプロイされたトリアージシステムが、あるグループの申請者に対して測定可能な不均衡な結果を生み出している。チームの立場は「自分たちはモデルをトレーニングしなかったのでモデルプロバイダーの問題だ」というものだ。この立場が間違っている理由は？
✓ 正解
不均衡な結果はオペレーターが所有する特定の箇所（取得ソース・プロンプトコンテンツ・閾値・ルーティングルール）で発生する。オペレーターはグループ間の結果を測定し、特定の決定を説明するためにそれをログに記録する責任がある
💡 暗記ポイント
公平性の責任はオペレーターにある。不均衡な結果はオペレーターが制御する箇所（取得ソース・プロンプト・閾値・ルーティングルール）で入る。結果ログなしには個別決定の説明もできない。「プロバイダーの問題」も「大きなモデルで解決」もどちらも誤り。
🇺🇸 English
A deployed triage system produces measurably worse outcomes for one applicant group. The team's position is that fairness is the model provider's problem, since they did not train the model. Why is this position wrong?
✓ Correct Answer
Unequal outcomes enter at identifiable points the operator owns—retrieval sources, prompt content, thresholds, and routing rules—so the operator must measure outcomes across groups and can only explain specific decisions if it logs them.
🔑 Key Words
fairness公平性グループ間で均等な結果を保証する設計原則
biasバイアス特定グループへの不均衡な影響・偏り
operator responsibilityオペレーターの責任取得・プロンプト・閾値での不均衡をオペレーターが対処
decision logging決定ログ個別決定の根拠を後から説明するためのログ記録

Q235Evaluation — Evals-First Development ★ CCAR-P 固有
🇯🇵 Japanese

✓ 正解

💡 暗記ポイント

A team plans to build a drafting assistant first and write evaluations "once there is something to test." What is the strongest argument against this ordering?
✓ Correct Answer
Evals defined before the build act as acceptance criteria and as the gating mechanism for every subsequent change; written afterward, they tend to describe what the system already does rather than what the business requires.
🔑 Key Words

The sustained quality decline, because it has crossed a committed SLA threshold and the SLA names what is owed when a breach occurs.
