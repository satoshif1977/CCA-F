Q201Agent Architecture & RAG Design
🇯🇵 Japanese
カスタマーサポートアシスタントが、夜間バッチでインデックス化した注文データベースのコピーに対して RAG パイプラインで「注文はどこですか？」に回答している。回答は流暢で自信に満ちているが、顧客が古い配送状況を受け取ることがあり、エラーシグナルは一切ない。根本原因に最も適切に対処する変更は？
✓ 正解
注文状況の照会はライブ注文システムへのツール呼び出しにルーティングし、取得は安定したポリシーコンテンツのために残す
💡 暗記ポイント
取得（RAG）は安定した知識に、ツール呼び出しは別システムが所有するライブの状態に使い分けるのが鉄則。夜間インデックスでは「正確だが古い」情報しか得られず、エラーシグナルもない。更新頻度を上げても（1時間ごと等）窓を狭めるだけで根本解決にはならない。
🇺🇸 English
A customer-service assistant answers "Where is my order?" using a RAG pipeline over a nightly-indexed copy of the order database. Answers are fluent and confident, but customers sometimes receive outdated shipping statuses with no error signal. Which change best addresses the root cause?
✓ Correct Answer
Route order-status lookups through a tool call to the live order system, keeping retrieval for stable policy content.
🔑 Key Words
retrieval (RAG)取得・RAG静的知識に対する検索拡張生成
tool callツール呼び出しライブシステムへのリアルタイム照会
staleness陳腐化キャッシュ・インデックスが古くなる問題
groundingグラウンディングモデル出力を事実ソースに基づかせること
Q202Agent Architecture — Agent vs Workflow
🇯🇵 Japanese
請求書処理ユースケースのステップは完全に列挙可能（フィールド抽出 → 発注書との照合 → 台帳へ転記）で、誤った転記は高額な監査を引き起こす。チームはエージェントとワークフローのどちらを選ぶか検討している。最も適切なパターンとその理由は？
✓ 正解
ワークフロー。パスが予測可能であり、エラーコストが高いステップ間に決定論的なガードを置けるため
💡 暗記ポイント
ステップが列挙可能 + エラーコストが高い = ワークフロー確定。エージェントの非決定論的なトラジェクトリリスクは、この場面では許容できない。エージェントはステップが不明・環境が動的・判断が必要な場合に選ぶ。
🇺🇸 English
An invoice-processing use case has fully enumerable steps (extract fields → validate against the purchase order → post to the ledger), and a wrong posting triggers a costly audit. Which pattern fits, and why?
✓ Correct Answer
Workflow, because the path is predictable and deterministic guards can sit between steps where error cost is high.
🔑 Key Words
workflowワークフローステップが固定・決定論的な自動化パターン
deterministic決定論的な同じ入力→同じ出力が保証される性質
enumerable steps列挙可能なステップあらかじめすべての手順が特定できる状態
guardガードステップ間のバリデーション・検証機構
Q203Agent Architecture — Orchestration & Fan-out
🇯🇵 Japanese
オーケストレーターが 40 件の文書レビューユニットをサブエージェントに展開し、出力を1つのレポートに統合する。本番環境で1ユニット欠落したままレポートが出荷された。再発を最も確実に防ぐ制御は？
✓ 正解
ディスパッチされたユニット ID と返されたユニット ID を比較するコードバウンダリでの決定論的な完全性チェックを統合処理の前に追加する
💡 暗記ポイント
ファンアウトの欠落はコードバウンダリで決定論的にチェックする。モデルへの自己チェック指示や、より大きなモデルへの切り替えは確率論的な解決策であり不十分。ファンアウト数削減は処理能力を下げるだけで検出を保証しない。
🇺🇸 English
An orchestrator fans out 40 document-review units to subagents and synthesizes their outputs into one report. In production, a report shipped with one unit silently missing. Which control most reliably prevents a recurrence?
✓ Correct Answer
Add a deterministic completeness check at the code boundary that compares dispatched unit IDs against returned unit IDs before synthesis runs.
🔑 Key Words
fan-outファンアウトタスクを複数サブエージェントに並列展開すること
completeness check完全性チェックすべての期待結果が揃っているか確認
orchestratorオーケストレーターサブエージェントを管理・統合する上位エージェント
code boundaryコードバウンダリコードレベルで実施する決定論的な制御点
Q204Solution Design — Non-determinism
🇯🇵 Japanese
あるアーキテクトはデモが5回クリーンに実行されたことを確認し、動作が決定論的だと結論づけ、各モデル出力を固定の再現可能な結果として扱う財務照合パイプラインをリリースした。2週間後、同じ明細書を再処理すると異なる分類が生成された。どの設計原則が違反されたか？
✓ 正解
デモは決定論を証明しない。非決定論的な出力には、アーキテクチャに評価と検証が組み込まれている必要がある
💡 暗記ポイント
デモの成功は決定論の証拠ではない。LLM は確率的コンポーネントであり、同じ入力が異なる出力を生む可能性がある。アーキテクチャレベルで評価・検証を組み込むことが必須。コンテキストウィンドウ不足・カットオフ・温度設定の記録不備は根本原因ではない。
🇺🇸 English
An architect watched a demo run cleanly five times, concluded the behavior was deterministic, and shipped a financial reconciliation pipeline that treats each model output as a fixed, repeatable result with no checks. Two weeks later, re-processing the same statement produced a different categorization. Which design principle was violated?
✓ Correct Answer
A demo is not evidence of determinism; non-deterministic outputs require evaluation and verification built into the architecture.
🔑 Key Words
non-determinism非決定論性同一入力でも異なる出力が生まれる LLM の性質
probabilistic確率論的出力に確率的ばらつきがある性質
verification検証出力が正しいことをアーキテクチャ内で確認する仕組み
evaluation評価モデル出力の品質・正確性を測定すること
Q205Models & Selection — Model Swap Governance
🇯🇵 Japanese
本番環境で Sonnet を運用しているチームが、レビュアーが「回答がより良くなる」と感じるという理由だけでデフォルトモデルを Opus に切り替えたい。何がこの変更を承認すべきか？
✓ 正解
このタスクにとって「より良い」の意味を定義する評価セット、および切り替え前に合意されたロールバック基準
💡 暗記ポイント
モデル切り替えはリリースと同等。定義された評価セットとロールバック基準なしのモデル変更は無管理のリスク。コスト比較のみは品質を無視、感覚ベースの投票は再現可能なゲートではない。「より高性能なモデルは常に安全」は誤り（タスク適合性・コスト・レイテンシーが変わる）。
🇺🇸 English
A team running Sonnet in production wants to switch the default model to Opus because reviewers "feel" the answers would be better. What should gate the change?
✓ Correct Answer
An eval set that defines what "better" means for this task, plus a rollback criterion agreed before the swap.
🔑 Key Words
eval set評価セットモデル変更の品質ゲートとなる評価用データセット
rollback criterionロールバック基準変更を元に戻す条件を事前に合意しておくこと
model tierモデルティア性能・コストが異なるモデルのグレード区分
model swapモデル切り替え使用モデルを別バージョン・グレードに変更すること
Q206Context Management — Progressive Loading
🇯🇵 Japanese
長期稼働するアシスタントが、すべての会話履歴とすべての取得コーパスをリクエストごとにロードする。短いセッションでは品質は良いが、長いセッションでは劣化し、一部のターンでは以前の内容がサイレントに失われる。このデプロイに最も適した戦略は？
✓ 正解
プログレッシブコンテキストローディング。各ステップで必要なものだけをモデルに渡し、ウィンドウがサイレントに満杯にならないようにする
💡 暗記ポイント
モノリシックな全履歴ロードは長期セッションでコンテキストウィンドウを必ず枯渇させる。プログレッシブローディングで各ターンに必要な情報だけを渡すのが正解。より大きなモデルは問題を遅らせるだけ（ハードな上限は変わらない）。取得を無効化すると必要なグラウンディングが失われる。
🇺🇸 English
A long-lived assistant loads the full conversation history and the full retrieved corpus into every request. Quality is fine in short sessions but degrades over long engagements, and some turns silently lose earlier material. Which strategy best fits this deployment?
✓ Correct Answer
Progressive context loading, so the model receives only what it needs at each step and the window does not fill silently.
🔑 Key Words
progressive loadingプログレッシブローディング各ステップに必要なコンテキストのみを段階的に提供
context windowコンテキストウィンドウモデルが一度に処理できるトークン数の上限
monolithic contextモノリシックコンテキスト全履歴・全コーパスを一括ロードする戦略
truncationトランケーションコンテキスト超過時に古い内容がサイレントに切り捨てられること
Q207Security & Integration — Server-side Authorization
🇯🇵 Japanese
チャットアプリがクライアントリクエストから 'role' 値を受け取り、それをシステムプロンプトに挿入し、取得レイヤーはロールに関係なくすべての文書を返す。最も深刻なセキュリティギャップを閉じる変更は？
✓ 正解
サーバー側でIDを確認し、サーバー（クライアントではなく）がロールと認可された文書セットを注入し、文書のアクセス制御を取得レイヤーで実施する
💡 暗記ポイント
ID・認可はサーバー側で強制する。クライアントから受け取った値をそのまま信頼するのは致命的な脆弱性。プロンプト指示でのロール制御は steerable（誘導可能）であり enforceable（強制可能）ではない。ログは事後的な検知にすぎず、モデル選択で認可境界は作れない。
🇺🇸 English
A chat application accepts a "role" value from the client request and injects it into the system prompt, and the retrieval layer returns any document regardless of role. Which change closes the most serious security gap?
✓ Correct Answer
Verify identity server-side, have the server (not the client) inject role and authorized document sets, and enforce document access control in the retrieval layer before content reaches the model.
🔑 Key Words
server-sideサーバー側認証・認可をクライアントでなくサーバーで実施
authorization認可リソースへのアクセス権を確認・制限すること
access controlアクセス制御役割・スコープに基づきデータアクセスを制限
steerable vs enforceable誘導可能 vs 強制可能プロンプト指示は誘導のみ・コードロジックが強制力を持つ
Q208RAG & Integration — Chunking Strategy
🇯🇵 Japanese
コーパスには意味のあるセクション・サブセクションを持つ構造化されたポリシーマニュアルがある。ユーザーはセクションレベルの義務を参照する質問をする。このコーパスに最も適したチャンキング手法は？
✓ 正解
セクションを保持し、適切なレベルで取得する階層的チャンキング
💡 暗記ポイント
構造が意味を持つ文書（ポリシーマニュアル等）では階層的チャンキングが最適。固定サイズチャンクは構造を無視して意味をぶった切り、意味的チャンキングは既存の有意義な構造を捨て、全文書チャンクはトークンバジェットを圧迫し関連性を希薄化する。
🇺🇸 English
A corpus consists of structured policy manuals with meaningful sections and subsections, and users ask questions that reference section-level obligations. Which chunking approach best fits this corpus?
✓ Correct Answer
Hierarchical chunking that preserves sections and retrieves at the level that fits.
🔑 Key Words
hierarchical chunking階層的チャンキング文書構造（章・節）を保持して分割する手法
structured document構造化文書章・節・サブセクションなど意味ある構造を持つ文書
retrieval level取得レベルセクション・段落など適切な粒度で取得する
semantic chunking意味的チャンキング意味の区切りで分割する手法（構造を持たない文書向け）
Q209RAG & Integration — Hybrid Retrieval
🇯🇵 Japanese
サポートナレッジベースには、言い換えられた自然言語の質問と正確な部品番号・エラーコードを含むクエリが混在している。Dense-only 取得は言い換えには強いが、正確コードのクエリを見逃す。適切な修正は？
✓ 正解
Dense と Sparse 取得を組み合わせ、Reciprocal Rank Fusion で結果をマージするハイブリッドインデックスに移行する
💡 暗記ポイント
部品番号・エラーコードなど正確トークンは Sparse（BM25）が強く、言い換えは Dense（埋め込み）が強い。混在する場合はハイブリッドインデックス + RRF が標準解。埋め込みモデルのファインチューニングは高コスト・低確実性。BM25 のみに切り替えると言い換えクエリが犠牲になる。
🇺🇸 English
A support knowledge base receives a mix of paraphrased natural-language questions and queries containing exact part numbers and error codes. Dense-only retrieval performs well on paraphrases but misses the exact-code queries. What is the appropriate fix?
✓ Correct Answer
Move to hybrid indexing that combines dense and sparse retrieval, merging results with reciprocal rank fusion.
🔑 Key Words
hybrid retrievalハイブリッド取得Dense と Sparse の両手法を組み合わせた取得
dense retrievalDense 取得埋め込みベクトルの近傍探索による意味的取得
sparse / BM25Sparse / BM25キーワード一致に基づく古典的情報検索
reciprocal rank fusion相互順位融合（RRF）複数ランクリストを統合するシンプルな手法
Q210Governance & Data Handling — PII
🇯🇵 Japanese
規制業種のデプロイメントで、トレースレビューにより顧客の氏名と口座番号がソースシステムからモデルのコンテキストウィンドウに直接流れていることが判明した。データ処理要件に最も適した修正は？
✓ 正解
コンテキストウィンドウにコンテンツが入る前に PII フィールドを仮名化または匿名化し、識別子の復元はモデル呼び出しの外で行う
💡 暗記ポイント
PII はコンテキストウィンドウに入れる前に仮名化・匿名化するのが正解。プロンプト指示での制御はモデルへの露出自体を防がない。トランスポート暗号化は別の脅威への対策。ログ保持期間短縮はプロンプトへの侵入を止めない。データ最小化がデータハンドリングの根本原則。
🇺🇸 English
In a regulated-industry deployment, a trace review shows customers' names and account numbers flowing directly from the source system into the model's context window. Which remediation best fits the data-handling requirement?
✓ Correct Answer
Redact or anonymize the PII fields before the content enters the context window, mapping identifiers back only outside the model call.
🔑 Key Words
PII個人識別情報氏名・口座番号など個人を特定できる情報
redaction仮名化・削除個人情報をマスクまたは削除して処理
anonymization匿名化識別子を除去・変換して個人を特定不能にすること
data minimizationデータ最小化必要な情報のみを収集・処理する原則
Q211Evaluation — Code-based vs Model-based Eval
🇯🇵 Japanese
必須フォーマットで引用を含める起草アシスタントの評価スイートを構築している。モデルベース評価ではなく、コードベース評価で採点するのに最も適した動作はどれか？
✓ 正解
引用が必須スキーマ（文書名・ページ番号・セクション）に準拠しているかどうか
💡 暗記ポイント
スキーマ準拠は決定論的。コードで正確・高速・低コスト・ドリフトなしに検証できる。トーン（適切か）・説得力・意図への忠実さは解釈が必要でモデルベース（または人間）評価が適切。コードで判断できる = 判定基準が明確で二値判定できるもの。
🇺🇸 English
A team is building an eval suite for a drafting assistant that must include citations in a required format. Which behavior is best graded with a code-based eval rather than a model-based one?
✓ Correct Answer
Whether the citations comply with the required schema (document name, page number, section).
🔑 Key Words
code-based evalコードベース評価ルール・正規表現・スキーマで判定する決定論的評価
model-based evalモデルベース評価LLM が採点者として品質を評価する手法
schema complianceスキーマ準拠定義した構造・フォーマットに従っているか
deterministic grading決定論的採点同一入力に対して常に同じ判定が得られる評価
Q212Evaluation — LLM-as-Judge
🇯🇵 Japanese
チームが LLM-as-judge を使用して出力品質を採点する計画。judge の評価を信頼できるものにする実践を2つ選べ。
※ 2つ選択
✓ 正解
A: judge を信頼する前に人間がラベル付けした出力セットでキャリブレーションする ／ B: 評価対象の出力を生成したモデルとは異なるモデルを judge として使用する
💡 暗記ポイント
Judge キャリブレーション（人間ラベルとの照合）と別モデル使用（自己嗜好バイアス防止）が2大原則。自由形式の 1〜100 スコアはドリフトしやすく一貫性がない（制約付き判定が望ましい）。同一モデルの judge は自分の出力を過大評価する自己嗜好バイアスが入る。
🇺🇸 English
A team plans to use an LLM-as-judge to grade output quality. Which TWO practices make the judge's verdicts trustworthy?
✓ Correct Answer
A: Calibrate the judge against a set of human-labeled outputs before relying on its scores. B: Use a different model as the judge than the one whose outputs are being evaluated.
🔑 Key Words
LLM-as-judgeLLM-as-judgeLLM が採点者として他モデルの出力を評価する手法
calibrationキャリブレーション人間ラベルと比較してjudgeの精度を事前確認
self-preference bias自己嗜好バイアス同一モデルが自分の出力を過大評価する傾向
constrained verdict制約付き判定自由スコアでなくカテゴリ・基準を限定した評価
Q213Evaluation — Shadow Testing
🇯🇵 Japanese
規制業種のデプロイメントで、未検証バージョンへのユーザー露出は不可。どの検証アプローチが適切か？
✓ 正解
シャドウテスト：新バージョンをライブトラフィックのコピーで実行し、ユーザーには現行バージョンのみを提供し、シャドウ出力をオフラインでスコアリングする
💡 暗記ポイント
露出不可 = シャドウテスト一択。A/B テストや早期採用者パイロットはユーザーを未検証バージョンに露出させる。シャドウテストのコストはダウンストリームのユーザーシグナルを失うことだが、この場合は許容。デプロイ後の苦情監視は事後的かつ無制御。
🇺🇸 English
A regulated-industry deployment with modest traffic needs to validate a prompt change, but exposing any user to an unvalidated version is not permissible. Which validation approach fits?
✓ Correct Answer
Shadow testing: run the new version on a copy of live traffic, serve users only the current version, and score the shadow outputs offline.
🔑 Key Words
shadow testingシャドウテスト本番トラフィックのコピーで新版を評価・ユーザーには旧版を提供
A/B testA/B テスト本番ユーザーを2群に分けて新旧バージョンを比較
validation検証変更が要件を満たすか確認するプロセス
regulated industry規制業種金融・医療など厳格なコンプライアンスが求められる業界
Q214Governance & Safety — Fail Closed
🇯🇵 Japanese
オペレーター構築の入力スクリーニング分類器がピーク時にエラーを起こし、現在アプリはこの状況でトラフィックをスクリーニングなしで通過させている。正しい評価は？
✓ 正解
guardrail がフェールオープンになっている。チームが構築・所有したスクリーニング制御は、コントロールが正常に戻るまでトラフィックをブロックするフェールクローズドにすべきだ
💡 暗記ポイント
フェールオープン（壊れたら通す）= guardrail の安心感なし・制御なし（むしろ危険）。スクリーニング制御はフェールクローズド（壊れたら止める）が正解。Anthropic のモデル安全性は別レイヤーであり、オペレーター構築のスクリーニングの代替にはならない。ログ取得は事後検知にすぎない。
🇺🇸 English
An operator-built input-screening classifier errors under peak load, and the application currently passes traffic through unscreened when this happens. What is the correct assessment?
✓ Correct Answer
The guardrail is failing open; for a screening control the team built and owns, it should fail closed, blocking traffic until the control is healthy again.
🔑 Key Words
fail closedフェールクローズド制御が失敗した場合にトラフィックをブロックする設計
fail openフェールオープン制御が失敗した場合にトラフィックを通過させる（危険）
