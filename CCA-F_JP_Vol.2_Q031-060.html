Q31 Agent architecture and orchestration
5交差点のセンサーログを現在直列処理中。
❓ Anthropicが推奨するマルチエージェント設計パターンを用いて並行実行にアーキテクチャを再設計するにはどうすればよいか？
✅ 正解
コーディネーターのシステムプロンプトを変更し、1回の応答ターン内で複数の Task ツール呼び出しを出力させて、5つのサブエージェントを並列に生成（スポーン）する。
Claudeは1回のレスポンスで複数のツールを同時に呼び出す機能（並列ツール呼び出し）をネイティブにサポートしており、これを利用して複数のワーカーエージェントを一度にトリガーするのが、オーケストレーター・ワーカーモデルにおける最も効率的で標準的なパターンです。
💡 暗記ポイント
Anthropicが推奨するオーケストレーター・ワーカーパターンでは「並列ツール呼び出し（Parallel Tool Calling）」を活用。
1回の生成ターン内で複数のTaskツール呼び出しを同時に出力させ、アプリケーション側で並行実行することでレイテンシを大幅削減できる。

18時間ごとのバッチ送信がSLAを保証できる最大間隔。

Q34 Prompt engineering and structured output
❓ ECサイトレビューの「期待通りではなかった」等の曖昧なレビューを文脈に応じて複数カテゴリに分類する際、精度を最も効果的に向上させるにはどうすればよいか？
✅ 正解

推論過程を含む Few-shot プロンプティングは、モデルが複雑なニュアンスや判断基準を学習するための最も確実な方法であり、ハルシネーションの抑制と精度の向上に大きく寄与します。
💡 暗記ポイント
曖昧なデータの分類精度向上に最も効果的なのは「推論プロセスを含むFew-shotプロンプティング」。
正解ペアに加え「なぜそのカテゴリを選んだか」の論理（Chain of Thought）を例示することで、類似の曖昧なケースでも正確な判断が可能になる。

Q36 Agent architecture and orchestration

❓ APIの制限を遵守しつつ最も効率的なリファクタリング戦略は？
✅ 正解
1日分48,000件のデータを蓄積し、1日1回、5つの独立したバッチ（例：10,000件を4つ、8,000件を1つ）として送信する。
Message Batches APIは1バッチにつき最大10,000件の制限があるため、48,000件を処理するには最小でも5つのバッチに分割する必要があります。
要件（1日1回の確認）を満たしつつ、管理オーバーヘッドを最小限に抑える設計です。
💡 暗記ポイント
Message Batches APIは1バッチ最大10,000件の制限がある。
1日あたり48,000件（2,000件×24時間）を処理するため、制限内で最小限のバッチ数に分割して送信し、1日1回の確認頻度に合わせて結果を回収するアーキテクチャが最適。

Q47 Context management and reliability
電子カルテ処理。
SLA60時間、10%が再試行必要。
Batch API最大24時間。
❓ すべてのカルテで60時間のSLAを確実に遵守するために設定できる「最大の」バッチ送信間隔は？
✅ 正解
12時間ごと
送信間隔を12時間にすることで、最悪のタイミングで到着したデータでも、最初の待ち（12h）＋ 1回目（24h）＋ 2回目（24h）＝ 60h となり、SLAを遵守できます。
また、1回目の終了時刻が次の送信タイミングと重なるため、再処理時の待ち時間をゼロに抑えられます。
💡 暗記ポイント
計算：60時間 - (24時間×2回) = 残り12時間が猶予。
最初の待ち時間（最大12時間）＋1回目（24時間）＋2回目（24時間）= 60時間。
12時間間隔なら失敗データを即座に次のバッチに含めて再処理開始でき、SLAを満たす最大間隔となる。

Q49 Agent architecture and orchestration
50ファイル超のPRレビューで個別ファイルの構文エラーは検出できるが、ファイル間の依存関係問題を見落とし注意力の分散で変数名を混同するハルシネーションが発生。
❓ ワークフローをどのように再設計すべきか？
✅ 正解
ワークフローを「ファイルごとの局所分析パス」と、それに続く「独立したファイル間統合パス」に分割する。
個別のファイル分析で詳細を詰め、その成果物（要約やメタデータ）を用いて別のステップで全体像を検証する「多段階プロセス」により、ハルシネーションを抑制しながら高度な依存関係チェックを実現できます。
