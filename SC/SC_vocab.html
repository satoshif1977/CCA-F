XSSCross-Site Scripting（クロスサイト・スクリプティング）
他人のブラウザで、攻撃者が書いたプログラムを勝手に動かす。
最頻出。公式解答例は一貫して「出力時にエスケープ処理を施す。」
攻撃者の script が被害者のブラウザで動くので、その人の権限でできることは何でもできる。cookie を盗む・画面を書き換える・勝手に送信する。だから対策は「入力を弾く」ではなく「画面に出す瞬間に記号を無害化する」。入力時のチェックは保険的対策にとどまる。R7秋問1では、アップロードした .xlsx の中身が JavaScript で、script タグから読み込まれていた。
反射型XSS
わなリンクを踏ませた、その場かぎりで動くタイプ。
3種の区別が2回名指しされた。ログ分析では攻撃の形が変わる。
URL に仕込んだ script が、そのままページに反射して返ってくる。わなリンクを踏ませる必要があるので、メールや SNS での誘導とセットになる。保存されないため、攻撃を受けたのはリンクを踏んだ人だけ。
格納型XSS
掲示板などに保存され、見た人全員で動くタイプ。
R5秋問1・R6秋問3。投稿機能があれば真っ先に疑う。
掲示板・レビュー・プロフィールなど、サーバに保存される場所に仕込む。保存されるので、そのページを見た人が全員やられる。被害が広がりやすく、インシデント対応では「いつから保存されていたか」の特定が要る。R5秋問1は商品レビュー、R6秋問3は EC サイトが舞台。
DOM Based XSS
サーバを通らず、ブラウザ内の処理だけで起きるタイプ。
DOM を使っていれば DOM Based、とは限らない。発生箇所で判断する。
サーバは正常な HTML を返しているのに、ブラウザ内の JavaScript が URL の一部などを画面に書き込む過程で発生する。サーバのログに痕跡が残りにくいのが厄介。「DOM を使っていたから DOM Based」と即断するのは誤りで、どこで script が注入されたかで判断する。
エスケープ処理
記号を「ただの文字」として扱うよう変換すること。
★「入力時」ではなく「出力時」。公式解答例はすべて出力時。
< を &lt; に、> を &gt; に変えるなど、記号を「表示用の文字」に置き換えること。出力先によって必要な変換が違う（HTML 本文・属性値・JavaScript 内・URL でそれぞれ別）。公式解答例は R5秋問1「レビュータイトルを出力する前にエスケープ処理を施す。」R7秋問1「出力時にエスケープ処理を施す。」と、一貫して出力時。
サニタイジング
危険な文字を取り除く・無害化すること。
エスケープとの違いを聞かれることがある。
危険そうな文字を削除・置換して無害化すること。エスケープが「意味を変えずに安全に表示する」のに対し、サニタイジングは「危険な部分を取り除く」。許可するタグだけ残す HTML サニタイザなどが該当する。
CSPContent Security Policy
読み込んでよいスクリプトの出どころを、サイト側が宣言する仕組み。
R7秋問1で「内容や緩和効果、CSP を回避する攻撃手法」まで理解を促された。
レスポンスヘッダで「script はこのドメインからだけ読み込む」と宣言し、注入された script の実行を防ぐ。ただし設定が緩いと回避される（信頼したドメインに攻撃者がファイルを置ける場合など）。R7秋問1の採点講評は「CSP の内容や緩和効果」に加えて「CSP による制御を回避する攻撃手法」まで理解するよう促している。
CSRFCross-Site Request Forgery（クロスサイト・リクエスト・フォージェリ）
ログイン中の人に、本人が気づかないまま操作を実行させる。
R6春問3。★トークンがあっても、攻撃者が自分の token を使えば破られる。
被害者のブラウザは正規の cookie を自動で送るため、サーバから見ると本人の操作に見える。だから「ログインしているか」では防げず、「その画面から来たか」を確かめる必要がある。R6春問3は、攻撃者が自分のアカウントで取得した csrf_token を使ってトークン検証をすり抜ける応用だった。
CSRFトークン
正規の画面から来たことを示す、使い捨ての合言葉。
「導入する」だけでは答えにならない設問がある。
フォームに埋め込んだ使い捨ての値を、送信時に照合する。セッションと結びついていないと、R6春問3のように攻撃者自身のトークンで突破される。SameSite=Lax/Strict と組み合わせるのが現在の定石。
SameSite属性
別のサイトから来たリクエストに cookie を付けない設定。
R5秋問1の公式解答例「スクリプトから別ドメインの URL に対して cookie が送られない仕組み」。
cookie に Strict / Lax / None を指定し、別サイト起点のリクエストに cookie を付けるかを制御する。CSRF の根本に効く。R5秋問1の公式解答例は属性名を直接書かせず「スクリプトから別ドメインの URL に対して cookie が送られない仕組み」という説明で答えさせた。
HttpOnly属性
JavaScript から cookie を読めなくする設定。
XSS で cookie を盗まれる被害を抑える。
document.cookie から読めなくなるため、XSS が成立しても cookie は盗まれにくくなる。ただし XSS 自体は防げない（画面の書き換えや勝手な送信は可能）ので、あくまで被害軽減。
Secure属性
HTTPS のときだけ cookie を送る設定。
HSTS とセットで問われやすい。
HTTP のときは cookie を送らない。盗聴による窃取を防ぐ。HSTS で HTTPS を強制し、Secure で平文送信を止める、という組み合わせで問われる。
セッションID
ログイン中であることを示す、サーバが配る整理番号。
R5秋問1では画像としてアップロードさせて盗む手口が出た。
サーバ側に保持した状態と結びつく識別子。これを知られた時点で、その人になりすませる。推測困難な値であること・HTTPS で送ること・ログイン時に再発行することの3点が基本。
セッションフィクセーション
攻撃者が用意した整理番号を使わせ、あとで乗っ取る。
R6秋問4の公式解答例「使用済みの sessionID を無効にした上で、新しい sessionID を発行」。
攻撃者が自分の知っているセッションIDを被害者に使わせ、被害者がログインした後でそのIDを使って乗っ取る。対策は「ログイン成功時に必ず新しいIDを発行する」。R6秋問4の公式解答例「使用済みの sessionID を無効にした上で、新しい sessionID を発行」がそのまま答え。
セッションハイジャック
整理番号を盗んで、その人になりすます。
XSS → cookie 窃取 → なりすまし の流れで出る。
XSS で盗む・通信を盗聴する・推測する、の3経路がある。R5秋問1では、XHR で取得したトークンと一緒にセッションIDをアイコン画像としてアップロードする、という工夫された手口が出た。
SQLインジェクション
入力欄にデータベースへの命令を混ぜ込む。
R6秋問3で穴埋め。対策はプレースホルダ。
入力値が SQL 文の一部として解釈されてしまうのが原因。文字列連結で SQL を組み立てている箇所が危ない。対策はプレースホルダ一択で、「エスケープする」「入力値を検証する」は保険的対策。R6秋問3では穴埋めで名称を答えさせた。
プレースホルダ
値を入れる場所を先に決めておき、あとから値だけ渡す書き方。
SQLインジェクションの根本対策。「バインド機構」も同義。
SQL の構文を先に確定させ、値は後から「データとして」渡すので、値が命令に化けない。静的プレースホルダ（DB 側で確定）と動的プレースホルダ（ライブラリ側）があり、前者がより安全。
OSコマンドインジェクション
入力値が OS への命令として実行されてしまう。
シェルを起動する関数を使わないのが根本対策。
system() や外部コマンド呼び出しに入力値が渡る箇所で起きる。シェル経由で実行するとメタ文字（; | & など）が効いてしまう。根本対策はシェルを使わない API を選ぶこと。
ディレクトリトラバーサル
../ などを使って、見せてはいけないファイルを取る。
「パス名パラメータの未チェック」として安全なウェブサイトの作り方 第1章にある。
ファイル名を外部から指定できる機能で、../ を使って想定外の場所を読まれる。根本対策は「外部からファイル名を指定させない」。やむを得ない場合は許可リストで照合する。
IDORInsecure Direct Object Reference（安全でない直接オブジェクト参照）
番号を1つずらすだけで、他人のデータが見えてしまう。
R7春問3「注文番号を 00000001 から順に増やしてダウンロードを試行する。」
URL やパラメータの ID を書き換えるだけで、他人のデータにアクセスできてしまう。認証は通っているので、ログを見ても異常に見えにくい。R7春問3は注文番号を連番で試す攻撃、R6秋問4は「求職者 ID が推測困難なものになるように生成方法を変更する」が公式解答例。
認可
ログインした人が「それを見てよいか」を判断すること。
★認証（誰か）と認可（何をしてよいか）の違いは頻出。
認証の次に来る判断。「この利用者は、このデータを見てよいか」をサーバ側で毎回確かめる必要がある。画面にボタンを出さないだけでは対策にならない（API を直接叩かれる）。
認証
その人が本人かどうかを確かめること。
認可と混同しない。
パスワード・証明書・生体など、本人確認の手段。認証が強くても認可が抜けていれば、ログインできる人は誰でも全データを見られる。
アクセス制御
誰が何にアクセスできるかを決めて守る仕組み。
安全なウェブサイトの作り方 第1章の11番目。Web系で2番目に多い。
安全なウェブサイトの作り方 第1章の11番目。Web 系では XSS に次いで出題が多い。R6春問1の JWT 検証、R6秋問4 の WebAPI の IP 制限・多要素認証、R7春問3 の連番推測が、すべてこの分類に入る。
HTTPヘッダインジェクション
応答ヘッダに改行を混ぜ、別のヘッダや本文を偽装する。
現行形式での出題実績はまだない。
リダイレクト先やファイル名をヘッダに出力する箇所で、改行（CR LF）を注入されると別のヘッダや本文を作れてしまう。現行の言語・フレームワークでは改行が自動で弾かれることが多い。
メールヘッダインジェクション
問い合わせフォームから宛先を追加され、迷惑メールの踏み台にされる。
現行形式での出題実績はまだない。
問い合わせフォームの入力値を宛先や件名に使っていると、改行で Bcc を追加される。メール送信ライブラリの正しい API を使えば防げる。
クリックジャッキング
透明な枠を重ねて、見えないボタンを押させる。
対策は X-Frame-Options / CSP の frame-ancestors。
被害者には別のページが見えているが、透明な iframe が重なっていて、実際には裏のボタンを押している。退会・送金・権限変更など「一度押すと戻せない」操作が狙われる。
X-Frame-Options
自分のページを他サイトの枠内に表示させない指定。
クリックジャッキング対策。
DENY なら一切、SAMEORIGIN なら同一オリジンのみ、iframe に入れることを許す。古い指定方法で、現在は CSP の frame-ancestors が推奨される。
frame-ancestors
CSP で「どのサイトなら枠に入れてよいか」を指定する項目。
X-Frame-Options の後継にあたる。
CSP の指定のひとつで、複数のオリジンを列挙できる点が X-Frame-Options より柔軟。両方ある場合は frame-ancestors が優先される。
バッファオーバーフロー
入れ物より大きいデータを入れて、隣の領域を壊す。
Web アプリでは出にくい。C/C++ の文脈。
確保した領域を超えて書き込み、戻りアドレスなどを上書きして任意のコードを実行させる。C/C++ など自分でメモリ管理する言語の話で、Web アプリの設問にはほぼ出ない。
HSTSHTTP Strict Transport Security
このサイトは必ず HTTPS で来てください、とブラウザに覚えさせる。
R6秋問4「M サイトへの接続を HTTPS に強制することができる。」
一度 HTTPS で接続すると、以後ブラウザが自動で HTTPS に切り替える。最初の1回を狙う攻撃（SSLストリップ）に効く。R6秋問4の公式解答例は「M サイトへの接続を HTTPS に強制することができる。」
X-Content-Type-Options
ファイルの種類をブラウザに勝手に推測させない指定。
R6秋問4「Content-Type ヘッダーで指定した MIME タイプを強制的に適用することができる。」
nosniff を付けると、ブラウザが中身を見て勝手にファイル種別を判断しなくなる。テキストとして置いたファイルが script として実行される事故を防ぐ。R6秋問4「Content-Type ヘッダーで指定した MIME タイプを強制的に適用することができる。」
MIMEスニッフィング
ブラウザが中身を見て、勝手にファイル種別を判断してしまうこと。
nosniff で止める。
サーバが text/plain と言っていても、中身が HTML らしければブラウザが HTML として描画してしまう挙動。アップロード機能と組み合わさると XSS になる。
Content-Type
これは画像です、これは HTML です、と伝えるラベル。
拡張子と中身が一致しているかの検証とセットで問われる。
レスポンスで「これは何のファイルか」を伝えるヘッダ。R7秋問1では、拡張子と中身が一致しているかを検査するのが公式解答例だった。宣言と実体の食い違いが攻撃の起点になる。
CORSCross-Origin Resource Sharing
別のサイトからデータを取ってよいか、サーバ側が許可する仕組み。
Same-Origin Policy の例外を作る仕組み。
ブラウザが別オリジンへの読み取りを制限しているところへ、サーバ側が Access-Control-Allow-Origin で例外を許可する仕組み。ワイルドカードや動的な反射設定にすると、どのサイトからでも読めてしまう。
同一オリジンポリシーSame-Origin Policy
別のサイトのデータは勝手に読めない、というブラウザの基本ルール。
オリジン＝スキーム＋ホスト＋ポート。
ブラウザの最も基本的な防御。これがあるから、わなサイトの JavaScript が銀行サイトの中身を読めない。XSS はこの壁の「内側」で動くので強力。
オリジン
https・ドメイン名・ポート番号の3つの組み合わせ。
WebAuthn でも「オリジンを確認する」が解答になった（R5秋問3）。
https://example.com:443 のように、スキーム・ホスト・ポートの3点が一致して初めて同一オリジン。R5秋問3の公式解答例「認証に用いる情報に含まれるオリジン及び署名をサーバが確認する仕組み」は WebAuthn の説明。
JWTJSON Web Token
ヘッダ・中身・署名の3つをつないだ、持ち運べる引換券。
R6春問1。ステートレスな API 認証で頻出。
ヘッダ・ペイロード・署名を . でつないだ文字列で、Base64URL されているだけなので中身は誰でも読める（暗号化ではない）。サーバが状態を持たずに済む反面、発行後の失効が難しい。R6春問1が題材。
alg=none
署名なしでも通してしまう、JWT の危険な設定。
R6春問1の公式解答例「NONE でないことを検証する。」
JWT のヘッダで alg を none にすると「署名なし」という意味になり、検証を素通りする実装がある。公式解答例は「JWT ヘッダ内の alg に指定された値」が「NONE でないことを検証する。」つまり受け取った側が alg を信用してはいけない。
RS256 / HS256
JWT の署名方式。RS256 は公開鍵方式、HS256 は共通鍵方式。
方式を取り違えさせる改ざんが成立しうる。
RS256 は公開鍵方式（秘密鍵で署名・公開鍵で検証）、HS256 は共通鍵方式。公開鍵を共通鍵として HS256 で検証させる「アルゴリズム混同」攻撃が知られている。サーバ側で使う方式を固定するのが対策。
クレーム

R6春問1「利用者 ID が mid の値と一致するかどうかを検証する処理」。
sub（利用者ID）・exp（期限）・aud（宛先）など、JWT に入れる情報のこと。R6春問1は「JWT に含まれる利用者 ID が mid の値と一致するかどうかを検証する処理」が抜けていた、という設問だった。署名が正しくても、中身が誰のものかは別途確かめる必要がある。
ステートレス

R6春問1の穴埋めで出題。
サーバが利用者ごとの状態を保持しない設計。スケールしやすい反面、失効やログアウトの実装が難しくなる。R6春問1の穴埋めで出題された。
OAuth 2.0
パスワードを渡さずに、他サービスへ「この範囲だけ許可」する仕組み。
★認可の仕組み。認証そのものではない。
「このアプリに、私の写真の読み取りだけ許可する」といった委譲の仕組み。パスワードを渡さずに済むのが利点。★認可の枠組みであり、これだけでは「誰がログインしたか」は分からない。
OpenID ConnectOIDC

OAuth との違いが問われやすい。
OAuth 2.0 に ID トークン（JWT）を足して、認証にも使えるようにしたもの。OAuth を認証に流用した実装は脆弱になりやすく、OIDC を使うべき、という文脈で問われる。
認可コードフロー
先に引換券をもらい、裏側でアクセストークンと交換する流れ。
最も安全とされる OAuth の流れ。
まず認可コードを受け取り、サーバ間の通信でアクセストークンと交換する。トークンがブラウザの URL に出ないので漏れにくい。スマホアプリでは PKCE を併用する。
アクセストークン
API を使うための、期限つきの通行証。
R7春問3「Authorization ヘッダーから取り出す」。
API 呼び出しのたびに Authorization ヘッダに載せる。R7春問3の公式解答例「C サービスに送られた HTTP リクエストの Authorization ヘッダーから取り出す。」期限を短くし、漏れても被害を限定するのが基本。
リフレッシュトークン
通行証が切れたとき、新しいものをもらうための券。
漏えい時の影響が大きい。
有効期限が長いので、漏れるとアクセストークンを作り放題になる。保管場所と失効の仕組みが問われる。
スコープ
この通行証で何をしてよいかの範囲。
最小権限の考え方と結びつく。
トークンに「読み取りだけ」「この範囲だけ」と制限を付ける。最小権限の原則をトークンに適用したもの。
PKCEProof Key for Code Exchange
引換券を横取りされても使えないようにする追加の鍵。
スマホアプリなど、秘密を保持できない環境で必須。
認可コードを横取りされても、元の検証値を知らなければトークンに交換できない。スマホアプリのように秘密鍵を安全に持てない環境では必須。
SAMLSecurity Assertion Markup Language
企業で使われる、XML ベースのシングルサインオンの仕組み。
OIDC との使い分けで問われる。
XML の署名付きアサーションをやり取りする。企業の社内システムで広く使われており、署名検証の不備が脆弱性になる。
SSOSingle Sign-On
一度ログインすれば、複数のサービスを使えるようにすること。
便利だが、破られたときの影響範囲が広い。
利便性は高いが、認証基盤そのものが単一障害点になる。多要素認証と組み合わせて守るのが前提。R7秋問3では、認証基盤の仕様を踏まえた代替策が問われた。
Cookie
ブラウザがサイトごとに保管する小さなメモ。
属性（HttpOnly / Secure / SameSite）が対策の核。
ドメインとパスの単位で送信先が決まる。属性（HttpOnly / Secure / SameSite）の組み合わせが、そのまま XSS・盗聴・CSRF の対策になる。
WAFWeb Application Firewall
Web への攻撃らしい通信を、手前で止める仕組み。
R6春問1「セキュリティ施策は導入前にトレードオフを検討」。根本対策ではない。
通信パターンから攻撃を推定して遮断する。脆弱性自体は残るので保険的対策。R6春問1の採点講評は「セキュリティ施策は導入前にトレードオフを検討してほしい」と書いており、利点と課題を両方言えるかが問われる。
フォールスポジティブ偽陽性
正常なものを「異常だ」と誤って止めてしまうこと。
R6春問2「正常な通信を異常として検知してしまう。」
検知を厳しくすると増える。業務が止まるので運用が回らなくなる。R6春問2の公式解答例「正常な通信を異常として検知してしまう。」
フォールスネガティブ偽陰性
本当の攻撃を見逃してしまうこと。
しきい値を緩めると増える。
検知を緩めると増える。攻撃を素通りさせる。フォールスポジティブとのトレードオフを説明できるようにしておく。
脆弱性診断
攻撃者の立場で弱点を探して報告すること。
R6秋問4の題材。診断ツールの検出結果から被害を想定させる。
ツールによる自動診断と、専門家による手動診断がある。R7秋問1の公式解答例は「S サービスの仕様を理解した専門家による脆弱性検査」で、ツールだけでは足りないことを示している。
SASTStatic Application Security Testing
動かさずに、ソースコードを読んで弱点を探す。
R7春問1で SAST/DAST/IAST の特徴理解を促された。
開発中の早い段階で回せるが、実際には到達しないコードも指摘する（誤検知が多い）。R7春問1の採点講評で3つの使い分けの理解を促された。
DASTDynamic Application Security Testing
実際に動かして、外から攻撃を試して弱点を探す。
本番に近い環境が要る。
実際に動かすので誤検知は少ないが、画面を辿れない部分は検査できない。リリース前の検証で使う。
IASTInteractive Application Security Testing
動かしながら、内部の動きも計測して弱点を探す。
SAST と DAST の中間。
テスト実行中にアプリ内部も観測するので、どのコードが原因かまで分かる。エージェントの導入が要る。
セキュアコーディング
最初から弱点を作らない書き方をすること。
R6春問4・R7秋問1の題材。
後から直すより、最初から作り込まないほうが安い。R7春問1の公式解答例「企画・設計工程からセキュリティ対策を組み込むという考え方」＝セキュリティ・バイ・デザインにつながる。
入力値検証
受け取った値が想定どおりかを確かめること。
保険的対策。根本対策は出力時の処理。
型・長さ・文字種・範囲を確かめる。許可するものを列挙する（許可リスト）ほうが、危険なものを挙げる（拒否リスト）より確実。
出力エンコーディング
画面に出すときに、記号を安全な形に変換すること。
XSS の根本対策。
出力先ごとに正しい変換を選ぶ必要がある。HTML 本文・属性値・JavaScript 内・URL で必要な処理が異なる。
例外処理
エラーが起きたときの後始末の書き方。
R6春問4「例外発生時の動作は脆弱性につながりやすい部分」。
想定外のときに何が起きるかは、攻撃者の関心事そのもの。エラーメッセージに内部情報を出す、途中で処理が止まって権限チェックを飛ばす、といった事故につながる。
finally
エラーが起きても必ず実行される後片付けの場所。
R6春問4の穴埋め。リソースリークを防ぐ。
例外が出ても出なくても必ず通る。ファイルや DB 接続の解放をここに書く。R6春問4の穴埋めで出題された。
リソースリーク
使い終わった資源を返さず、だんだん足りなくなること。
finally で解放するのが基本。
解放し忘れが積もると、接続数の上限に達してサービスが止まる。可用性への影響なので、セキュリティの問題として扱われる。
ファイルアップロード
利用者がサーバにファイルを置ける機能。
R7秋問1「拡張子と整合しているかをチェックする。」
受け取ったファイルが実行される・そのまま配信される経路があると危険。拡張子だけでなく中身を検査し、公開ディレクトリに置かず、実行権限を与えないのが基本。R7秋問1はこれが主題。
Webスキミング
決済画面に仕込んだ script で、カード情報を外部へ送る。
R6秋問3の題材。EC サイトで起きる。
決済ページの JavaScript を改ざんし、入力されたカード情報を外部へ送る。サーバ側のデータベースは無傷なので気づきにくい。R6秋問3の公式解答例は addEventListener で form の submit を捕まえ、クエリパラメータとして外部へ送る手口だった。
addEventListener
ボタンを押したときなどに動く処理を登録する命令。
R6秋問3の公式解答例に登場。form の submit を横取りする。
イベントが起きたときに動く処理を後から追加できる。攻撃者がこれを使うと、既存の画面を壊さずに情報だけ抜ける。
DOMDocument Object Model
ページの中身をプログラムから触れるようにした構造。
R6秋問3「HTML、DOM の仕組みを利用した画面の書換えは攻撃で悪用される」。
HTML を木構造として扱えるようにしたもの。R6秋問3の採点講評は「HTML、DOM の仕組みを利用した画面の書換えは攻撃で悪用されるので、よく理解してほしい」と明記している。
ECMAScript
JavaScript の仕様そのもの。
★公式の出題趣旨で3回「読み解いて」と書かれている。
★出題趣旨に3回「HTML 及び ECMAScript を読み解いて」と書かれている。短いスクリプトを読んで、何が起きるかを言語化する練習が要る。
XHRXMLHttpRequest
ページを切り替えずに裏側で通信する古い仕組み。
R5秋問1の公式解答例に登場。
ページ遷移せずにサーバと通信する。現在は Fetch API が主流だが、過去問には XHR が登場する。
署名付きURL
期限つきで、その人だけが使える一時的なダウンロード用アドレス。
R7春問3。★生成はサーバ上で行う。アプリ上は解析される。
有効期限と対象を署名で固定した URL。★生成に使う鍵をアプリ側に置くと解析されるため、サーバ上で生成して配る。R7春問3の採点講評は「秘密情報の処理をサーバ上で完結させ安全を確保する実装は、クライアントサーバ型でも採用される基本的な方法」と書いている。
WebView
アプリの中に埋め込まれたブラウザ画面。
R7春問3「URL の先頭が https://www.a-sha.co.jp/ であるかを検証する。」
アプリ内ブラウザ。表示する URL を外部から指定できると、偽ページを表示されたりトークンを抜かれたりする。R7春問3の公式解答例「WebView を呼び出す前に、URL の先頭が https://www.a-sha.co.jp/ であるかを検証する。」
クレデンシャル
ID とパスワードなど、本人であることを示す情報一式。
R6春問3では IMDS から奪う流れで出た。
ID とパスワード、アクセスキー、トークンなど。R6春問3では SSRF で IMDS を叩き、クラウドの一時認証情報を奪う流れだった。どこに保管し、誰が取り出せるかが論点になる。
最小権限の原則
必要な分だけ権限を与えること。
Web でもクラウドでも共通の答え。
権限を絞っておけば、破られたときの被害が小さい。IAM・DB ユーザ・ファイル権限・API スコープなど、あらゆる層で答えになる。
多層防御
1つ破られても次で止まるよう、守りを重ねること。
根本対策と保険的対策の組み合わせ。
根本対策で塞ぎ、保険的対策で被害を抑え、検知で気づく。1つの対策を万能のように書くと減点されやすい。
根本対策
脆弱性そのものをなくす直し方。
安全なウェブサイトの作り方 の用語。保険的対策と区別する。
脆弱性そのものをなくす直し方。プレースホルダ、出力時エスケープ、認可チェックの追加など。公式解答例は基本的にこちらを求める。
保険的対策
脆弱性は残るが、被害を軽くする対策。
WAF などが該当。「根本対策ではない」と問われる。
脆弱性は残るが被害を減らす。WAF の導入、エラーメッセージの抑制、権限の最小化など。「根本対策か保険的対策か」を区別して書けるようにしておく。

管理・運用・脆弱性管理 60語

20問中6問。R7で急増した分野

CVECommon Vulnerabilities and Exposures
見つかった弱点ひとつひとつに付ける世界共通の番号。
「どの脆弱性か」を一意に指す。深刻度は表さない。
採番するのは MITRE で、番号そのものに危険度の意味はない。CVE-2026-12345 のように年と連番で付く。同じ製品の別の弱点には別の番号が付くので、資産管理台帳と突き合わせる鍵になる。
CVSSCommon Vulnerability Scoring System
弱点の深刻さを 0〜10 の点数で表す物差し。
R7春問4の穴埋めは「4.0」。★最新は v4.0。
基本値・現状値・環境値の3層でできている。基本値だけを見て優先度を決めると、実際には悪用されていない弱点に労力を使うことになる。R7春問4の穴埋めは版数の「4.0」だった。
CVSS 基本値Base Score
弱点そのものの性質だけで決まる点数。時間が経っても変わらない。
現状値・環境値との違いを押さえる。
攻撃元区分・攻撃条件の複雑さ・必要な特権・利用者の関与と、機密性/完全性/可用性への影響から算出する。公表時点で決まり、以後変わらない。
CVSS 現状値Temporal Score
攻撃コードが出回ったかなど、そのときの状況を反映した点数。
R7春問2「公開サイトにある情報から判断する必要がある」＝手間がかかる。
攻撃コードが公開されたか、修正プログラムが出たか、といった状況で上下する。★R7春問2は「手間が掛かる理由」を問い、公式解答例は「攻撃コードなどの情報を多くの公開サイトにある情報から判断する必要があるから」。自分で調べる必要があるので重い。
CVSS 環境値Environmental Score
自社の環境での重要度を加味した点数。
同じ脆弱性でも組織によって優先度が変わる根拠。
その弱点のある機器が社内でどれだけ重要かを加味する。同じ CVE でも、インターネット公開サーバと閉域の検証機では優先度が変わる、という説明に使える。
ACAttack Complexity（攻撃条件の複雑さ）
攻撃を成功させるのがどれくらい難しいか。
★R7春問2で C と取り違える誤答が多かった指標。
Low なら誰でも再現できる、High なら特定の条件が揃わないと成立しない。★R7春問2では、この AC を問うたのに C（機密性への影響）と答えた受験者が多かったと採点講評に書かれている。
AVAttack Vector（攻撃元区分）
どこから攻撃できるか。ネットワーク越しか、手元からか。
ネットワーク越しほど危険度が高い。
Network / Adjacent / Local / Physical の4段階。インターネット越しに攻撃できるものが最も危険度が高い。
PRPrivileges Required（必要な特権レベル）
攻撃に権限が要るかどうか。
権限不要ほど危険。
None なら権限不要、Low なら一般利用者、High なら管理者が必要。None が最も危険。
UIUser Interaction（利用者の関与）
利用者が何か操作しないと成立しないか。
関与不要ほど危険。
None なら利用者が何もしなくても成立、Required ならリンクを踏むなどの操作が要る。
C / I / AConfidentiality / Integrity / Availability
機密性・完全性・可用性への影響度。
★AC（攻撃条件）と C（機密性）は別物。
機密性（見られる）・完全性（書き換えられる）・可用性（止まる）。情報セキュリティの3要素そのもの。これに真正性・責任追跡性・否認防止・信頼性を加えて7要素とすることもある。
EPSSExploit Prediction Scoring System
その弱点が実際に攻撃される確率の予測値。
R7春問2「FIRST のサイトで公開されている値をそのまま使えばよい」＝手間がかからない。
今後30日以内に悪用される確率を、実際の観測データから予測する。★公式解答例は「FIRST のサイトで公開されている値をそのまま使えばよいから」＝調べる手間がかからない点が CVSS 現状値との違い。
KEVKnown Exploited Vulnerabilities
実際に悪用が確認された弱点の一覧（米CISA が公開）。
R7春問4「KEV カタログが現状の評価に活用される」。
「理論上危ない」ではなく「実際に攻撃されている」ものだけが載る。載っていれば最優先で対処する、という判断に直結する。R7春問4の採点講評が名指しした。
JVNJapan Vulnerability Notes
日本の脆弱性情報ポータル。JPCERT/CC と IPA が運営。
R7春問3の出題趣旨に名指しで登場。
日本語で読めるのが利点。製品ベンダーとの調整を経て公開されるため、対策情報と一緒に出てくることが多い。R7春問3の出題趣旨に名指しで登場した。
NVDNational Vulnerability Database
米国の脆弱性データベース。CVE に CVSS 値が付く。
JVN iPedia と並ぶ情報源。
CVE に対して CVSS の基本値を付与して公開する。JVN iPedia は NVD の情報も取り込んでいる。
FIRSTForum of Incident Response and Security Teams
CVSS や EPSS を策定・公開している国際団体。
R7春問2の公式解答例に登場。
CVSS の仕様策定と EPSS の公開を行っている。R7春問2の公式解答例に名前が出た。
SBOMSoftware Bill of Materials（ソフトウェア部品表）
そのソフトが何の部品でできているかの一覧表。
★R7春問1は「定義ではなく利点」を問うた。影響有無を容易に把握できる、が答え。
★R7春問1の採点講評は「SBOM の利用方法が説明できておらず、SBOM の定義を記載しただけの解答が散見された」と明記している。つまり「部品表です」では0点。公式解答例は「利用しているソフトウェアやそのバージョンが明確になり、脆弱性の影響有無を容易に把握できるから」。新しい CVE が出たとき、自社が影響を受けるかを即座に判定できる点が利点。
ASMAttack Surface Management
外から見えてしまっている自社の資産を洗い出して管理すること。
R7春問4の題材。未把握の公開 IT 資産を見つける。
自分たちが把握していない公開資産こそ危ない、という発想。キャンペーン用に立てて忘れたサイト、退職者が契約したサービスなどが典型。R7春問4の題材。
アタックサーフェス攻撃対象領域
攻撃者から狙える入口の広がり。
減らすことが対策になる。
公開ポート・公開サーバ・利用中の SaaS・従業員のアカウントまで含む。使っていないものを閉じるのが最も確実な対策。
サブドメインテイクオーバー
使わなくなったサブドメインを他人に乗っ取られること。
R7春問4「終了したサブドメインの CNAME レコードを削除する。」
CDN やクラウドのサービスを解約したのに、DNS の CNAME がそのサービスを指したまま残ると、第三者が同じ名前で再取得して自社ドメインのページを乗っ取れる。R7春問4の公式解答例は「終了したサブドメインの CNAME レコードを削除する。」
CNAME
あるドメイン名を別の名前の別名として設定する DNS の記録。
消し忘れがテイクオーバーの原因になる。
別名を指すレコード。指し先が消えても CNAME 自体はエラーにならないため、放置に気づきにくい。
WHOIS
ドメインやIPアドレスの登録者を調べる仕組み。
R7春問4の穴埋め。資産の棚卸しに使う。
誰がいつ登録したかが分かるので、把握していないドメインを見つける手がかりになる。R7春問4の穴埋め。
ポートスキャン
どの通信口が開いているかを外から調べること。
R7春問4「Web のポートだけが開いていることを確認する。」
開いている通信口を調べる。R7春問4の公式解答例は「ポートスキャンで Web のポートだけが開いていることを確認する。」まず何が動いているかを確かめてから、脆弱性スキャナを掛ける、という順序が問われた。
脆弱性スキャナ
既知の弱点がないかを自動で調べる道具。
ポートスキャンの次の段階として出た。
既知の弱点のパターンと照合する。未知の弱点は見つけられない。診断後に「実際に悪用できるか」を確認すると、優先度の判断材料になる（R7春問2）。
ペネトレーションテスト侵入テスト
実際に攻撃を試して、本当に侵入できるか確かめること。
脆弱性診断より踏み込む。
目的を決めて、実際に侵入できるかを試す。脆弱性診断が「弱点の洗い出し」なのに対し、こちらは「到達できるか」を確かめる。
パッチマネジメント
修正プログラムを漏れなく当てていく運用。
資産管理ができていないと成立しない。

R7春問3「AES-CBC で復号する」。
共通鍵暗号の標準。鍵長は128/192/256ビット。利用モード（CBC・GCM など）とセットで安全性が決まる。

前のブロックと混ぜながら暗号化する利用モード。
初期ベクトル（IV）が必要。
前のブロックの暗号文と混ぜてから暗号化する。R7春問3では、アプリ内に埋め込まれた共通鍵と初期ベクトルを解析して、暗号化されたアクセスキーを復号する手口が出た。

暗号化のはじめに使う、毎回変えるべき値。
使い回すと同じ平文が同じ暗号文になる。
毎回変える必要がある。固定したり使い回したりすると、同じ平文が同じ暗号文になり、内容を推測されるきっかけになる。
RSA
大きな数の素因数分解の難しさを使う公開鍵暗号。
署名にも暗号化にも使える。
鍵長2048ビット以上が目安。署名にも鍵交換にも使えるが、処理は重い。
楕円曲線暗号ECC
短い鍵で RSA と同等の強さを出せる公開鍵暗号。
モバイルや IoT で有利。
256ビットで RSA 3072ビット相当とされる。処理が軽いのでモバイルや組込みで使われる。
ハッシュ関数
どんな長さのデータも、決まった長さの要約値に変える関数。
元に戻せない。改ざん検知に使う。
同じ入力からは必ず同じ値が出て、わずかな違いで全く別の値になる。元に戻せない（一方向性）ことと、同じ値になる別の入力を見つけにくい（衝突困難性）ことが要件。
SHA-256
いま標準的に使われるハッシュ関数。
R6春問4の穴埋めは SHA-256 / SHA-384 / SHA-512。
現在の標準。MD5 や SHA-1 は衝突が見つかっており、使ってはいけない。R6春問4の穴埋めは SHA-256 / SHA-384 / SHA-512 のいずれか。
ソルト
パスワードに混ぜる、利用者ごとに違う追加の文字列。
同じパスワードでも違うハッシュになる。
利用者ごとに違う値を混ぜるので、同じパスワードでも違うハッシュになる。レインボーテーブルによる一括解析を防ぐ。
ストレッチング
ハッシュ計算を何度も繰り返して、総当たりを遅くすること。
ソルトとセットで問われる。
ハッシュ計算を数千〜数万回繰り返して、1回あたりの時間を意図的に長くする。総当たり攻撃の効率を下げる。
デジタル署名
秘密鍵で署名し、公開鍵で検証する。本人が出したことを示す。
★改ざん検知＋否認防止。MAC との違いが名指しで出た。
秘密鍵で署名し、公開鍵で検証する。署名できるのは秘密鍵を持つ本人だけなので、★改ざん検知に加えて否認防止ができる。ここが MAC との決定的な違い。
メッセージ認証符号MAC（Message Authentication Code）
共通鍵を使って、改ざんされていないことを確かめる値。
★R7秋問2で「デジタル署名」と誤答が多かった。否認防止はできない。

HMACHash-based MAC
ハッシュ関数を使って作る MAC。
JWT の HS256 の中身。
ハッシュ関数と共通鍵を組み合わせて MAC を作る方式。JWT の HS256 がこれ。
公開鍵証明書
この公開鍵は確かにこの人のものだと、第三者が保証する書類。
サーバ証明書もこの一種。
公開鍵と所有者情報に、認証局が署名したもの。これがあるから「この公開鍵は確かにこのサーバのもの」と信じられる。
認証局CA（Certificate Authority）
証明書を発行する、信頼される第三者。
ルート認証局と中間認証局がある。
証明書を発行し、失効情報を公開する。ルート認証局の秘密鍵が漏れると、信頼の連鎖全体が崩れる。
ルート証明書
信頼の起点となる、認証局自身の証明書。
★R7春問3「端末にインストールすると検証エラーが解消する」＝TLSインスペクションと同じ。
ブラウザや OS に最初から入っている信頼の起点。★ここに自前の証明書を入れると、その認証局が発行した証明書をすべて信じるようになる。R7春問3の公式解答例「通信解析ツールのプライベート認証局のルート証明書をインストールし、信頼設定を行う。」TLS インスペクションと同じ原理。
証明書チェーン
サーバ証明書からルートまで、信頼をたどる道筋。
どこか欠けると検証に失敗する。
サーバ証明書 → 中間認証局 → ルート認証局 と遡って検証する。中間証明書の配信漏れは、よくある設定ミス。
サーバ証明書の検証
信頼できる認証局の発行か・名前が一致するか・期限内かを確かめる。
★R5秋問2「具体的にどういった事項を検証するのかまで含めて」。
★R5秋問2の講評は「具体的にどういった事項を検証するのかということまで含めて、よく理解しておいてほしい」と書いている。公式解答例は「信頼された認証局から発行されたサーバ証明書ではない」「記載されているサーバ名は、接続先のサーバ名と異なる」の2点。偽サイトは正規の証明書を用意できないため、HTTPS であれば検証に失敗する。

無効になった証明書の一覧。
サイズが大きくなりやすい。
失効した証明書の一覧をまとめて配布する。件数が増えるとサイズが大きくなり、取得も重くなる。
OCSPOnline Certificate Status Protocol

CRL との使い分けが問われる。
1件ずつ問い合わせるので軽いが、検証のたびに通信が発生する。応答をサーバ側で添付する OCSP Stapling もある。

R5秋問3「使う利点に加えて、暗号技術の適正な利用方法についても」。

知識・所持・生体のうち2つ以上を組み合わせる認証。

知識（パスワード）・所持（スマホ・トークン）・生体（指紋）のうち2つ以上。同じ要素を2つ重ねても多要素にはならない。R6秋問4の公式解答例「ログインの認証を、多要素認証に変更する。」

30秒ごとに変わる使い捨ての数字。
★R5秋問3「偽サイトに入力された TOTP を、有効な間に使う」＝フィッシングに弱い。

★R5秋問3でクライアント証明書認証などと誤認する解答が多かった。

R5秋問3の講評で「新たな方式も登場し、普及し始めている」。

どちらの責任かを問われる。
物理・ハイパーバイザは事業者、OS より上は利用者、というのが IaaS の基本線。「クラウドだから安全」とは言えない根拠になる。

上に行くほど利用者の責任範囲は狭い。

長期キーを置かないための仕組み。
数時間で失効するので、漏れても被害が限定される。ロールと組み合わせて使うのが現在の標準。

仮想サーバが自分の情報や認証情報を取り出せる内部の窓口。

公開バケットなどを検出する。

コンテナ

★R5秋問3「どのような権限や仕組みによって実行されるか」。
