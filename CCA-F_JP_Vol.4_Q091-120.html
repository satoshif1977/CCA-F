Q91 Claude Code configuration and workflows
手動でECSサービスを更新し新しいタスクARNで初期化された。
❓ 古いARNが古いコンテキストに残っている状態で、修正を確認するためにClaudeとの作業をどのように進めるべきか？
✅ 正解
コンテキストウィンドウ内の古いタスクARNやイベントは古くなっておりハルシネーションを引き起こす可能性があるため、以前のクラッシュと新しいイメージタグの構造化された要約を使用して新しいセッションを開始する。
外部のシステム状態が非連続的にリセットされた場合、無効になった情報をコンテキストから排除するために新しいセッションを開始し、必要な背景情報のみを要約として渡すのが最も安全で確実なアプローチです。
💡 暗記ポイント
環境の外部状態が大きく変化しコンテキスト内の情報（古いARN・ログ）が無効（Stale）になった場合、そのままセッションを再開するとモデルが古いIDを参照してハルシネーションやエラーを起こす可能性が高い。
無効な過去の文脈を引き継がずに必要な要約だけを持って新しいクリーンなセッションを開始するのがベストプラクティス。

Q92 Prompt engineering and structured output
植物学フィールドノートで「一握り」「カゴ一杯」等の曖昧な量表現が「500g」「10メートル」等の標準単位に変換（ハルシネーション）されてしまう。
❓ 記述通りに抽出するための最も効果的な方法は？
✅ 正解
変換を行わずに、曖昧な測定表現をそのまま抽出する Few-shot 例（具体例）を使用する。
Few-shot プロンプティングは、モデルに特定の出力形式や制約（この場合は「変換しない」）を理解させるための最も確実な手法です。具体的な入出力例を提示することで、モデルはタスクの意図（変換ではなく正確な転記）を明確に学習できます。

標準単位への変換を防ぐにはFew-shotプロンプティングが最適。
特に曖昧な単位をそのまま出力しているパターンを含む具体的な入出力例を提示することで、モデルに「変換ではなく正確な転記」という意図を明確に学習させハルシネーションを抑制できる。
変換テーブルをシステムプロンプトに追加するとかえって変換を助長してしまうため逆効果。

Q97 Prompt engineering and structured output
構造化データ抽出の再試行ループで、誤った圧力値を修正せず全く新しい部品を捏造するハルシネーションが発生する。
❓ 再試行実装の最も可能性が高い欠陥は？
✅ 正解
再試行のプロンプトに具体的な検証エラーは含まれているが、失敗したJSON抽出結果が含まれていないため、モデルが特定のフィールドを修正するのではなく、一から抽出をやり直してしまっている。
失敗した出力をプロンプトに含めない場合、モデルは「修正」ではなく「再抽出」を行ってしまい、複雑な文書からの情報の拾い直しによって捏造や不整合が発生しやすくなります。
💡 暗記ポイント
再試行ループでは「何が間違っていたか」だけでなく「以前に何を生成したか（失敗した出力結果）」もプロンプトに含めることが不可欠。
以前の出力が提供されないと一から抽出し直す必要があり不整合や捏造リスクが高まる。
既存の出力を提示し「修正」するよう促すことで一貫性を保ちエラー箇所のみを正確に正せる。

まれな副作用は特定できたが特定の患者ID番号が完全に欠落してしまい安全性の追跡調査に使えなくなった。
❓ 再帰的な圧縮プロセス全体でプロビジョンスを維持するための最も効果的な変更は？
✅ 正解

構造化出力を利用してデータとソースIDをセットで扱い、ReduceフェーズでIDの配列を結合（マージ）していくことで、情報の圧縮とトレーサビリティの維持を両立できます。
💡 暗記ポイント
再帰的な要約の過程で元のデータの参照元（ID等）が欠落しやすい問題。
各ステップ（Map・Reduce）で構造化データ（JSON等）を使用し、発見された内容とソースIDのペアを維持・継承させる設計が不可欠。
最終的な出力まで確実なトレーサビリティが確保される。

Q110 Tool design and MCP integration
❓ MCPツール内部でネットワーク瞬断の一時的なエラーをローカルリトライで処理することの、アーキテクチャ上の主な利点は？
✅ 正解
繰り返されるエラーログやリトライコマンドによって、エージェントのコンテキストウィンドウやトークン制限が消費されるのを防ぐことができる。
エージェントを介さずにツール内でリトライを完結させることで、冗長なエラーメッセージによるコンテキストの浪費を回避し、エージェントを本来の目的である高レベルなタスクに集中させることができます。
💡 暗記ポイント
ネットワーク瞬断のような一時的エラーをツール側で自己完結的に処理することでエージェントの効率性を維持できる。
毎回エラーをエージェントに報告すると会話のターンが無駄に増えコンテキストが不要なログで埋まりトークンコストも増大する。
ツール内部のリトライが「低レベルなノイズ」からエージェントを保護する。

Q112 Context management and reliability
Message Batches APIで20,000件のブランド言及を非同期処理。
結果は非同期で返り順序が前後する可能性がある。
❓ 感情分析結果を元の投稿レコードと正確に紐付ける正確なデータマッピングを保証するには？
✅ 正解
データベースの主キーをバッチリクエストの custom_id フィールドに設定し、処理完了後にその ID を使用してレスポンスを元のデータと紐付ける。
custom_id フィールドは、非同期なバッチレスポンスを元のリクエストデータと確実に相関させるために用意された専用の識別子です。
💡 暗記ポイント
Message Batches APIでは結果が入力順に返る保証はない。
各リクエストのcustom_idフィールドにDBの主キー等を格納することで、モデルの出力に頼らずシステム的にレスポンスと元のレコードを一意に相関させることができる。

Q113 Agent architecture and orchestration
5つのECサイトの競合価格を逐次処理中。
❓ システム全体のレイテンシを削減するためにエージェントフレームワークを使用して並行実行に再設計するにはどうすればよいか？
✅ 正解
単一の回答ターン内で、それぞれが5つのサイトのいずれかを対象とする複数の独立した Task ツール呼び出しを出力するように、コーディネーターのシステムプロンプトを修正する。
Claudeに複数の独立したタスクを同時に生成（ツール呼び出し）させ、それらをランタイム側で並列に実行する「Parallelization（並列化）」パターンを採用することで、正確性を保ちつつ全体の処理時間を最小限に抑えることができます。
💡 暗記ポイント
独立した複数のサブタスクが存在する場合、1回の回答ターンで複数の異なるツール呼び出しを同時に出力するClaudeの「並列ツール呼び出し」能力を活用する。
エージェントフレームワーク側で並列実行するように実装するのが最も効率的で「エージェントらしい」並行処理の設計パターン。

Q114 Tool design and MCP integration
在庫管理エージェントのMCPツールでサービスアカウントの認証情報が期限切れで認証失敗。
エージェントのクラッシュを防ぐため全例外をキャッチして {isError: false, results: []} を返すように設定した。
❓ この設計がアーキテクチャに与える影響は？
✅ 正解

エラーを正常な空の結果としてマスクすることは「サイレント・フェイラー」を引き起こす。
ClaudeはisError: falseと空配列を受け取ると「データが存在しない」と誤った結論を導く。
エラー状態を正しくモデルに伝え、問題を報告・回復できるよう設計することが不可欠。

Q115 Prompt engineering and structured output
独自の産業用センサーデータのテレメトリ形式をJSONに変換するため詳細なプロンプトで説明したが、ネストされた括弧の処理方法を一貫して誤解してしまう。
❓ Claudeの変換ロジックを最も効果的に修正する手法は？
✅ 正解
変換要件を明確にするために、生のデータ行とそれに対応する正確な期待される JSON 出力の具体例を2〜3個提供する。
Few-shot 例を提供することで、言葉では伝えにくい複雑な変換ロジックや特殊なデータ構造（ネストされた括弧など）を Claude に正確に理解させることができます。

複雑な構文解析ルールを自然言語の説明だけで完璧に理解させるのが難しい場合、Few-shotプロンプティングが最も強力。
「変換前の生データ」と「期待されるJSON出力」のペアを提示することでモデルは言葉で説明しきれないパターンの法則性を実例から学習できる。

Q117 Context management and reliability
5万件の通話ログをバッチ処理後、300件がcontext_length_exceededエラーで失敗した。
❓ 最もコスト効率が良くアーキテクチャとして適切な失敗処理の方法は？
✅ 正解
失敗したリクエストを custom_id で特定し、該当する元のドキュメントを分割（チャンク化）して、分割されたドキュメントのみを新しいバッチで送信する。
失敗した分のみをターゲットにし、エラーの原因（長すぎるコンテキスト）をチャンク化で解消してからバッチAPIで再処理するのが最も効率的で健全な設計です。
💡 暗記ポイント
バッチ全体の再実行はコストの無駄。
失敗したリクエストをcustom_idで特定し、それらのドキュメントを分割（チャンク化）してコンテキスト内に収まるようにした上で、失敗分のみを新しいバッチとして再送信するのが最適。
バッチAPIの割引価格（50%オフ）を維持しつつエラーの根本原因を解決できる。

Q119 Agent architecture and orchestration
20個のIaCテンプレートを1プロンプトに結合→個別ファイル内の記述ミスを見落とし、ファイル間のリソース依存関係エラー（循環参照等）を検出できない。
❓ 最適なアーキテクチャ変更は？
✅ 正解
レビューを2段階に分ける：各ファイルの局所的な問題を特定する並列プロンプトを実行し、その後に要約とインターフェース情報のみを抽出してファイル間のデータフローや依存関係を確認する単一の統合プロンプトを実行する。
並列化（Parallelization）によって各ファイルの細部への注意を確保しつつ、要約された情報を用いて全体像の整合性を効率的に検証するマルチフェーズ構成により、問題が解決されます。
💡 暗記ポイント
局所的な検証（構文チェック）と高次の検証（システム全体の依存関係）は異なる抽象度のタスク。
①各ファイルを個別に精査する「並列処理フェーズ」→②要約・インターフェース情報のみを統合して全体をレビューする「統合フェーズ」を組み合わせるワークフローが精度と信頼性を両立させるベストプラクティス。

Q120 Claude Code configuration and workflows
Claude Code を CI/CD パイプライン（GitHub Actions等）に統合するとジョブが常にハングアップ（停止）してしまう。
❓ 最も可能性の高い原因と解決策は？
✅ 正解
コマンドに -p または --print フラグを含めて、Claude Code を非インタラクティブモードで実行する必要がある。
-p (--print) フラグを使用することで、対話セッションを開始せずに1回限りのタスクとしてプロンプトを実行・出力できるため、CI/CD パイプラインでの自動化に不可欠な設定です。
💡 暗記ポイント
Claude Codeのデフォルトはインタラクティブ（対話型）モードで、ユーザーからの入力を待ち受けるためCI等のヘッドレス環境では処理が停止する。
解決策：-p または --print フラグを使用して非インタラクティブモードでプロンプトを実行し、標準出力に結果を返して直ちに終了させる。
