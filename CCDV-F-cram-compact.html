1. Applications & Integration (33%) 最重要

Messages API

  • POST /v1/messages — 必須: model / max_tokens / messages
  • 必須ヘッダー: x-api-key, anthropic-version, content-type
  • messages = user/assistant の配列。最初は必ず user
  • API はステートレス — 会話履歴は毎回全部送る
  • system はトップレベルパラメータ（messages の中ではない）

stop_reason

値意味
end_turn自然完了
max_tokens出力上限で打ち切り → max_tokens 増/streaming
stop_sequenceカスタム停止シーケンスに到達
tool_useツール呼び出し要求 → 実行して tool_result を返す
pause_turnサーバー側ツール一時停止 → そのまま再送で再開
refusal安全上の拒否 → 同じプロンプトで再試行しない

主要機能

  • Streaming: SSE。message_start → content_block_start → content_block_delta → content_block_stop → message_delta → message_stop
  • Vision: base64 or url の image ブロック / PDF は document ブロック
  • サードパーティ: Bedrock（anthropic. プレフィックス・SigV4）/ Vertex AI（GCP ADC）/ Microsoft Foundry

Batch API 頻出

  • 50% 割引 / 24時間以内 / 最大 100,000件 or 256MB
  • 結果は 29日間取得可 / 順序保証なし → custom_id で突き合わせ
「大量」+「急がない」+「コスト最優先」→ Batches API
「ユーザーが待っている」「対話型」→ リアルタイム + streaming

HTTP エラーコード

コード種別リトライ
400パラメータ不正しない
401API キー不正しない
403権限不足しない
404モデル ID タイポ等しない
413リクエスト大きすぎしない（入力を減らす）
429rate_limitする（retry-after）
500api_errorする

Application Design (8.6%)

  • 5つのインターフェース: Claude Code / Claude Desktop / claude.ai / API / SDKs
  • content boundaries: 信頼できる指示(system) と信頼できないデータ(user) を分離。XML タグで境界明示
  • session hygiene: 無関係なタスクは新しいセッションで
  • model version pinning: 本番は特定バージョンにピン留め
  • prompt versioning: プロンプトもバージョン管理 → 評価 → デプロイ

2. Model Selection & Optimization (17%)

LLM 基礎

  • temperature: 低=決定的、高=多様。temperature=0 でも完全な決定性は保証されない
  • zero-shot（例なし）/ single-shot（例1つ）/ multi-shot = few-shot（例複数）

モデルオプション 4種

オプション要点
extended thinkingbudget_tokens で思考量を明示指定（旧世代）
adaptive thinkingthinking: {type: "adaptive"} モデルが自律決定（4.6以降推奨）
effort levelslow / medium / high / xhigh / max の5段階
fast mode最大2.5倍速（Opus系限定・プレミアム価格）

Opus / Sonnet / Haiku

ティア特性ユースケース
Opus最高性能・最高価格複雑な推論、長時間エージェント
Sonnetバランス本番大量ワークロード
Haiku最速・最安分類、ルーティング、レイテンシ重視
  • 定番: ルーティング構成（Haiku が振り分け → 難しいものだけ Opus/Sonnet）

Prompt Caching 最重要

  • プレフィックス一致。前方の1バイトでも変わると後方すべて無効
  • レンダリング順: tools → system → messages。安定を前に、可変を後ろに
  • cache_control: {type: "ephemeral"} でブレークポイント（最大4つ）
  • TTL: デフォルト 5分（1hオプション）
  • 書込 1.25倍（1h は 2倍）/ 読取 0.1倍 → 最大 ~90% 削減
  • system に datetime.now() を入れるとキャッシュ毎回無効（silent invalidator）

3. Agents & Workflows (15%)

ワークフロー vs エージェント

  • ワークフロー: 事前定義されたコードパス。手順が決まっている場合
  • エージェント: LLM が動的に決定。オープンエンドなタスク
  • 原則: 最もシンプルな構成から始める
  • エージェント判断基準4つ: 複雑性 / 価値 / 実行可能性 / エラー回復可能性

ワークフローパターン 5つ

パターン内容
Prompt chaining順次ステップ、前の出力→次の入力
Routing入力を分類→適切な処理へ振り分け
Parallelization独立サブタスク並列/多数決
Orchestrator-workers中央LLMが動的分解→ワーカー委任
Evaluator-optimizer生成+評価ループで品質改善

エージェント構築

  • Claude Agent SDK: 組込ツール(Read/Write/Edit/Bash/Glob/Grep/WebSearch/WebFetch) + エージェントループ + hooks + subagents + MCP
  • エージェントループ: モデル呼出 → tool_use → ツール実行 → tool_result 返却 → end_turn で終了
  • subagents: コンテキスト分離・並列化・専門化
  • hooks: 決定論的な処理を差し込む（LLM 判断に依存しない強制制御）
  • デプロイ: Anthropic-hosted（インフラ管理不要）/ self-hosted（データを自社管理下）

4. Prompt & Context Engineering (11%)

Context Engineering

  • context bloat: 不要なツール出力で圧迫→性能低下
  • context drift: 長いセッションで指示からズレる
  • 対策: tool output pruning（刈込）/ compaction（要約）/ context isolation（サブエージェント分割）

Prompt Engineering

  • 明確・直接的な指示が最優先
  • few-shot 例示 → 出力形式・スタイルの安定に最も効果的
  • system: 役割・ルール・安全制約 / user: タスク入力・データ
  • XML タグでデータと指示を構造化して分離

Output Handling

  • structured outputs: JSON Schema（output_config.format）/ ツール入力は strict: true
  • defensive parsing: try-catch で JSON.parse / json.loads
  • 自信ありげな出力でも間違いうる（ハルシネーション）→ 検証・出典確認

5. Tools & MCPs (11%)

Tool Implementation

  • 定義 = name + description + input_schema
  • description が最重要: いつ呼ぶべきかを書く
  • tool_choice: auto / any / tool / none
  • 並列ツール: 複数 tool_use → 全結果を1つの user メッセージでまとめて返す
  • エラーは is_error: true で返す（握りつぶさない）
  • client-side: 自コードが実行 / server-side: Anthropic 側（web search, web fetch, code execution）

MCP (Model Context Protocol) 頻出

  • 目的: 外部連携を標準化 → 複数アプリで再利用・独立保守
プリミティブ内容制御主体
toolsモデルが呼ぶ関数モデル制御
resources読取用データ・コンテキストアプリケーション制御
prompts再利用可能テンプレートユーザー制御
  • 通信: stdio（ローカル）/ ネットワーク（リモート・HTTP/SSE）

Agentic Customization 4者 頻出

手段使いどころ
built-in tools汎用操作（ファイル・bash・Web検索）
custom tools自社固有のアクション・API
Skills手順・ノウハウのパッケージ化（知識）
MCP外部連携を標準プロトコルで再利用可能に
「アクション追加」→ tool / 「手順を教える」→ Skill / 「複数アプリで再利用」→ MCP

6. Security & Safety (8%)

プロンプトインジェクション 頻出

  • 外部コンテンツに埋め込まれた指示がモデルを乗っ取る攻撃
  • 正解パターン: (1) untrusted 扱い+分離 (2) hooks/guardrails で強制ブロック (3) 最小権限
  • ダミー: temperature 調整（無関係）/ 「無視しないで」お願い（強制力なし）/ 指示追従的モデル（かえって脆弱化）

Guardrails

  • 多層化: 入力検証 → プロンプト設計 → モデル安全性 → 出力検証 → hooks → 監査ログ
  • PII: 収集最小化、ログ混入防止、メモリに PII を保存しない

Hooks（セキュリティ文脈）

  • 「プロンプトで禁止する」より「フックで物理的に止める」が正解

Key Management

  • API キーをハードコードしない → 環境変数 or シークレットマネージャー
  • 認証(authentication) = 誰か / 認可(authorization) = 何ができるか

7. Claude Code (3%)

  • コアコンポーネント5つ: Rules / Skills / Commands / Agents / Agent Memory
  • CLAUDE.md 階層: エンタープライズ → プロジェクト(./CLAUDE.md) → ユーザー(~/.claude/CLAUDE.md)
  • ヘッドレスモード: claude -p "プロンプト" → CI/CD・自動化
  • スラッシュコマンド: 組込 + カスタム（.claude/commands/）

8. Eval, Testing & Debugging (3%)

  • まず HTTP エラー(4xx/5xx) か モデル出力の問題かを区別
  • 切り分け: 生リクエストをログ → API 直接呼びで再現確認
  • trace analysis: エージェントの実行トレースでどのステップで壊れたか特定
  • リカバリ: リトライ（指数バックオフ）/ フォールバックモデル / 人間エスカレーション
