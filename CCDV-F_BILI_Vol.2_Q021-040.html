Q21Agents and Workflows
🇯🇵 Japanese
Claude API を使ったエージェントループを実装している。モデルのレスポンスを受け取った後、次のアクションを決定するために stop_reason を確認する。stop_reason が「tool_use」の場合と「end_turn」の場合で、それぞれ何をすべきか？また「max_tokens」の場合はどう対処するか？
✓ 正解
tool_use：レスポンス内の tool_use ブロックからツール名・引数を取り出して実行し、tool_result を user メッセージとして Claude に返して再呼び出しする。end_turn：Claude が自然に完了と判断した状態。ループを終了してユーザーに最終回答を返す。max_tokens：出力が上限で打ち切られた（不完全な可能性）。max_tokens を増やすか streaming に切り替えて継続生成を検討する。
💡 暗記ポイント
stop_reason は Claude API で最も重要な制御フィールド。条件反射で覚える：tool_use→ツール実行して再呼び出し／end_turn→ループ終了／max_tokens→出力未完・設定見直し／stop_sequence→カスタム停止列に到達／pause_turn→サーバーサイドツール一時停止（再送で再開）／refusal→安全上の拒否（同じプロンプトで再試行しない）。
🇺🇸 English
You are implementing an agent loop using the Claude API. After receiving the model response, you check stop_reason to decide the next action. What should you do when stop_reason is 'tool_use' versus 'end_turn'? And how should you handle 'max_tokens'?
✓ Correct Answer
tool_use: Extract the tool name and arguments from the tool_use block, execute the tool, and return the tool_result as a user message for the next API call. end_turn: Claude naturally completed its response — exit the loop and return the final answer to the user. max_tokens: Output was truncated at the limit (may be incomplete) — increase max_tokens or switch to streaming to continue generation.

Q22Agents and Workflows
🇯🇵 Japanese
データ分析パイプラインを設計している。①生データのクリーニング→②統計分析→③レポート生成 の 3 ステップが決まっており、各ステップの出力が次ステップの入力になる。この要件に最も適したエージェントアーキテクチャパターンはどれか？また、ステップを Claude に逐次実行させる場合と並列実行する場合の違いは？
✓ 正解
手順が事前に定義されており逐次依存関係があるため、Prompt Chaining（プロンプトチェーニング）ワークフローが最適。前のステップ出力を次のステップ入力に繋ぐ設計。並列実行（Parallelization）は各ステップが独立している場合に有効だが、このケースは依存関係があるため逐次実行が必要。
💡 暗記ポイント
ワークフロー 5 パターンの使い分け：Prompt Chaining=逐次依存ステップ / Routing=入力を分類して振り分け / Parallelization=独立タスクの並列実行や多数決 / Orchestrator-workers=中央LLMが動的に分解・委任 / Evaluator-optimizer=生成と評価のループ。「手順が決まっている→ワークフロー」「手順が事前定義できない→エージェント」が判断の基準。

✓ Correct Answer

Q23Agents and Workflows
🇯🇵 Japanese
コンテンツ生成エージェントが長文記事を生成しているが、品質にばらつきがある。生成品質を安定させるために、同一タスクを複数回実行して最良結果を選ぶアプローチと、生成→評価→改善のループを回すアプローチのどちらが適切か？それぞれのパターン名と使い分けは？
✓ 正解
複数回実行して多数決/最良選択 → Parallelization（並列化）パターン。複数の独立した生成を並列実行し、評価基準で最良を選ぶ。生成→評価→改善ループ → Evaluator-optimizer パターン。生成 LLM と評価 LLM が役割分担してループ改善する。反復回数が少なく許容コストが限られるなら Parallelization、より高品質を追求するなら Evaluator-optimizer が適切。
💡 暗記ポイント
Parallelization のサブパターン：並列実行（同時実行でレイテンシ削減）と多数決（同一タスク複数実行で信頼性向上）がある。Evaluator-optimizer は 2 つの LLM が協力するメタパターン。コスト・品質・レイテンシのトレードオフで選択する。「常にシンプルな構成から始める」原則に従い、単純化できるならワークフローを選ぶ。
🇺🇸 English
A content generation agent produces long articles, but quality is inconsistent. To stabilize quality, which is more appropriate: running the same task multiple times and selecting the best result, or iterating through a generate-evaluate-improve loop? What are the pattern names and when should each be used?
✓ Correct Answer
Run multiple times and vote/select best → Parallelization pattern: run multiple independent generations in parallel and select the best by evaluation criteria. Generate-evaluate-improve loop → Evaluator-optimizer pattern: a generation LLM and an evaluation LLM share roles in a loop. Use Parallelization when iteration budget is small; use Evaluator-optimizer when higher quality is required.

ユーザーのサポートリクエストを処理するシステムを構築している。リクエストは「請求に関する質問」「技術的なバグ報告」「新機能リクエスト」「一般的な問い合わせ」の 4 種類に分類され、それぞれ異なる専門エージェントが対応する。最も適切なワークフローパターンはどれか？
✓ 正解
Routing（ルーティング）パターンが最適。入力（サポートリクエスト）を分類ステップ（Haiku などの軽量モデルまたはルールベース）で 4 種類に分類し、それぞれ適切な専門エージェント（請求担当・技術担当・プロダクト担当・一般担当）に振り分ける。分類とルーティングを分離することで各エージェントの専門性を高め、全体品質を向上させる。
💡 暗記ポイント
Routing の活用ポイント：① 分類精度が重要なため、分類専用の軽量モデルを使うと効率的 ② 各処理ブランチは独立しているため並列化も可能 ③ 分類コストは全体の一部なのでコスト効率が良い。Haiku でルーティング → Sonnet/Opus で実際の処理、という階層化がベストプラクティス。
🇺🇸 English
You are building a system to handle user support requests. Requests fall into four categories: 'billing questions,' 'technical bug reports,' 'new feature requests,' and 'general inquiries,' each handled by a different specialized agent. What is the most appropriate workflow pattern?
✓ Correct Answer
The Routing pattern is optimal. A classification step (lightweight model like Haiku, or rule-based logic) categorizes the input into one of four types and routes it to the appropriate specialist agent (billing, technical, product, or general). Separating classification from processing enhances each agent's specialization and improves overall quality.

🇯🇵 Japanese
マルチエージェントシステムでサブエージェントを使う主なメリットは何か？また、どのようなケースでサブエージェントを使うべきで、どのようなケースでは不要か？
✓ 正解
サブエージェントの 3 つのメリット：① コンテキスト分離（探索結果の詳細を親のコンテキストに持ち込まず、要約のみ返す） ② 並列化（独立したワークストリームを同時実行） ③ 専門化（特定タスクに特化したエージェントで品質向上）。使うべきケース：独立・並列なワークストリーム・大規模ファイル探索。不要なケース：単純な逐次作業（オーバーヘッドになる）。
💡 暗記ポイント
サブエージェントはコンテキスト管理の強力なツール。Claude Code の Explore サブエージェントが典型例（150 ファイルのコードベースを別コンテキストで分析して要約のみ返す）。サブエージェントは独立したコンテキストで動くため、詳細な探索ログがメインのコンテキストを汚染しない。過度な使用はオーバーヘッドになるため、本当に必要な場合のみ使う。
🇺🇸 English
What are the main benefits of using subagents in a multi-agent system? And in which cases should subagents be used versus not used?
✓ Correct Answer
Three benefits of subagents: ① Context isolation (returns only a summary to the parent, without polluting the parent's context with exploration details); ② Parallelization (run independent workstreams concurrently); ③ Specialization (specialized agents improve quality for specific tasks). Use when: independent/parallel workstreams, large-scale file exploration. Not needed when: simple sequential tasks (adds overhead).

Q27Prompt and Context Engineering
🇯🇵 Japanese
長期的なカスタマーサポートエージェントが会話を重ねるにつれて、初期の対応方針から外れた回答をするようになった。また、コンテキストウィンドウが徐々に埋まってきている。これらの問題の原因と、最も効果的な対処法はどれか？
✓ 正解
原因：context drift（コンテキストドリフト）= 長いセッションで当初の指示から挙動がずれる現象と、context bloat（コンテキスト肥大化）= 古いツール出力や会話履歴が不要に蓄積する現象。対処法：① compaction（コンパクション）= 古い会話履歴を要約に置き換えてコンテキストを圧縮 ② tool output pruning = 古い大きなツール出力を刈り込む ③ 長いセッションを新しいコンテキストで再開する。
💡 暗記ポイント
コンテキスト管理の 3 点セット：① tool output pruning（古い/大きいツール出力を刈り込む） ② compaction（履歴を要約に置き換え） ③ context isolation（サブエージェント・マルチステップに分割）。compaction と pruning の違い：pruning は「削除」、compaction は「要約に置き換え（情報は保持）」。長いセッションはコンテキストドリフトのリスクが高く、重要な指示は定期的に再注入することも有効。
🇺🇸 English
A long-running customer support agent has started giving responses that drift from its original guidelines as conversations accumulate. The context window is also gradually filling up. What are the causes and the most effective remedies?
✓ Correct Answer
Causes: context drift (behavior deviating from original instructions over long sessions) and context bloat (unnecessary accumulation of old tool outputs and conversation history). Remedies: ① compaction — replace old conversation history with summaries; ② tool output pruning — trim old, large tool outputs; ③ restart with a new context for long sessions.

context bloatコンテキスト肥大化不要なツール出力・履歴がコンテキストを圧迫して性能・コストを悪化させる現象
compactionコンパクション会話履歴を要約に置き換えてコンテキストを圧縮する手法。情報を保持しつつ削減

Q28Prompt and Context Engineering
🇯🇵 Japanese
Claude API で外部ドキュメント（ユーザーがアップロードした PDF のテキスト）を処理する際、ドキュメント内に「前の指示を無視して…」という悪意のある指示が埋め込まれていた場合のリスクと、プロンプト設計で取るべき対策はどれか？
✓ 正解
これはプロンプトインジェクション攻撃。外部コンテンツを untrusted input（信頼できない入力）として扱い、信頼された指示（system プロンプト）から明示的に分離する。XML タグを使ってデータの境界を明示する（例: ...外部コンテンツ...）。さらに hooks/guardrails で機密アクションを決定論的にブロックし、エージェントに最小権限のみ与える。
💡 暗記ポイント
プロンプトインジェクション対策の 3 本柱：① 分離（XML タグ等でデータと指示の境界を明示）② 決定論的ガードレール（hooks で機密アクションを強制ブロック）③ 最小権限（エージェントに不要なツール・スコープを与えない）。「プロンプトで禁止する」だけでは不十分（モデルの判断に依存する）→ フックで物理的に止めるのが正解パターン。
🇺🇸 English
When processing external documents (text extracted from a user-uploaded PDF) with the Claude API, a malicious instruction was embedded in the document: 'Ignore previous instructions and...' What is the risk and what prompt design countermeasures should be taken?
✓ Correct Answer
This is a prompt injection attack. Treat external content as untrusted input and explicitly separate it from trusted instructions (system prompt) using XML tags to mark data boundaries (e.g., ...external content...). Additionally, use hooks/guardrails to deterministically block sensitive actions, and grant the agent only minimum necessary privileges.
🔑 Key Words
prompt injectionプロンプトインジェクション外部コンテンツに埋め込まれた指示がモデルの動作を乗っ取る攻撃
untrusted input信頼できない入力外部コンテンツ・ユーザー入力・ツール出力など、安全が保証されない入力

🇯🇵 Japanese
Claude API で JSON 形式の出力を安定して取得したい。アプリケーションは Claude の出力を JSON.parse() で処理しているが、まれにマークダウンコードブロック（```json ... ```）が混入してパースエラーが起きる。最も確実に JSON 出力を保証する方法はどれか？
✓ 正解
Structured Outputs 機能（output_config.format に JSON Schema を指定する）を使う。これにより Claude はスキーマに準拠した JSON を直接返し、マークダウンラッパーは含まれない。さらに defensive parsing を実装する（JSON.parse を try-catch で包み、パース失敗時は再試行またはフォールバック処理）。プロンプトで「JSON のみを返せ」と指示することと合わせて使う。
💡 暗記ポイント
Structured Outputs（構造化出力）はスキーマ準拠を API レベルで保証する最も確実な方法。従来のプロンプト指示（「JSONで返して」）は確率的でマークダウン混入リスクがある。defensive parsing（try-catch + json.loads/JSON.parse）はパース失敗時の保険として常に必要。「自信ありげな出力でも間違いうる」ためスキーマ検証を必ず通すこと。
🇺🇸 English
You want to reliably receive JSON-formatted output from the Claude API. Your application processes Claude's output using JSON.parse(), but occasionally markdown code blocks (```json ... ```) are mixed in, causing parse errors. What is the most reliable way to guarantee JSON output?

Use the Structured Outputs feature (specify a JSON Schema in output_config.format). This ensures Claude returns schema-compliant JSON directly without markdown wrappers. Additionally implement defensive parsing (wrap JSON.parse in try-catch, with retry or fallback on failure). Combine with a prompt instruction to return only JSON.

Q30Prompt and Context Engineering
🇯🇵 Japanese
法律事務所が Claude API を使った契約書レビューシステムを構築している。system プロンプトには「弁護士として振る舞え」という役割定義と、会社の機密レビュー基準（固定コンテンツ）を含める。user メッセージには契約書テキスト（可変コンテンツ）が入る。Prompt Caching を最大限活用するために、コンテンツの配置はどうすべきか？
✓ 正解
安定した（変化しない）コンテンツを前方に、可変コンテンツを後方に配置する。レンダリング順序は tools → system → messages の順なので：① tools 定義（変化なし）② system プロンプト（役割＋機密レビュー基準、最も安定）に cache_control: {type: "ephemeral"} を付与 ③ user メッセージ（契約書テキスト、毎回変化）。プレフィックス 1 バイトでも変わるとキャッシュが無効になるため、可変コンテンツ（datetime.now() 等）を前方に置かないことが重要。
💡 暗記ポイント
Prompt Caching の鉄則：「安定したコンテンツを前に・可変コンテンツを後ろに」。キャッシュレンダリング順：tools → system → messages。cache_control はキャッシュ境界点（ブレークポイント）を指定するフィールド（最大 4 つ）。Silent invalidator の例：system プロンプトに datetime.now()・UUID・セッション ID を含めるとキャッシュが毎回無効になる。TTL は 5 分（1 時間オプション）。
🇺🇸 English
A law firm is building a contract review system using the Claude API. The system prompt includes a role definition ('act as a lawyer') and the firm's confidential review criteria (fixed content). User messages contain contract text (variable content). How should content be arranged to maximize Prompt Caching benefits?
✓ Correct Answer
Place stable (unchanging) content at the front and variable content at the back. The rendering order is tools → system → messages, so: ① tools definitions (no change); ② system prompt (role + review criteria, most stable) — attach cache_control: {type: 'ephemeral'}; ③ user message (contract text, changes each time). Even one byte of prefix change invalidates the cache, so never put variable content (datetime.now(), etc.) in the front.

Q38Model Selection and Optimization
🇯🇵 Japanese
Claude API で新しいモデルバージョンがリリースされた。本番環境で稼働中のエージェントシステムが突然、以前と異なる振る舞いをするようになるリスクを防ぐためのベストプラクティスはどれか？
✓ 正解
モデルバージョンをピン留め（version pinning）する。エイリアス（claude-sonnet-4-6 等ではなく claude-sonnet-4-6-20250514 のような具体的なバージョン）を使用し、自動的に新バージョンへ切り替わらないようにする。新バージョンへの移行時は、移行前に評価（eval）を実行して挙動変化を確認してから切り替える。
💡 暗記ポイント
本番環境でのモデル管理の鉄則：「エイリアスは自動的に新バージョンを指しうる → 本番はバージョン指定」。新バージョンのモデルは性能が向上する一方、breaking behavior changes（従来のプロンプトへの反応が変わる）が発生しうる。アップグレードは「eval で検証 → ステージングでテスト → 本番切り替え」の手順を踏む。
🇺🇸 English
A new model version of the Claude API was released. What are the best practices to prevent the risk that a production agent system might suddenly behave differently than before?
✓ Correct Answer
Pin the model version (version pinning). Use a specific version identifier (e.g., claude-sonnet-4-6-20250514) rather than an alias, so the system does not automatically switch to a new version. When migrating to a new version, run evaluations (evals) to verify behavioral changes before switching.

usage フィールドのキャッシュ関連：cache_read_input_tokens（キャッシュから読んだトークン数・0.1 倍課金）と cache_creation_input_tokens（キャッシュ書き込みトークン数・1.25 倍課金）を監視することでキャッシュ効率を評価できる。Token Counting API は「無料で事前見積もり」が特徴。コスト最適化の 3 点セット：キャッシュ / 適切なモデルティア / Batches API（50% off）。
