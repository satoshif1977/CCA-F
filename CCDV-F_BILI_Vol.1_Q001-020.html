Q1Applications and Integration
🇯🇵 Japanese
SaaS 企業がユーザーのサポートチケットを Claude API で分析するシステムを構築している。チケットは毎日夜間に 80,000 件まとめて届き、翌朝までに全件のカテゴリ分類と優先度スコアが必要だ。コストを最小化しつつ要件を満たす最適な API 利用パターンはどれか？
✓ 正解
Message Batches API（バッチ API）を使用する。通常の Synchronous API と比べて最大 50% のコスト削減が可能で、24 時間以内の応答が保証されるため夜間バッチ処理に最適。1 バッチに最大 100,000 リクエストまたは 256 MB まで含めることができるため、80,000 件は 1 バッチで送信可能。
💡 暗記ポイント
Message Batches API はバルク・非同期処理向けに設計されており、通常料金の半額で利用できる。上限は 100,000 リクエストまたは 256 MB/バッチ。結果は 29 日間保持され、custom_id で各結果を突き合わせる。リアルタイム性が不要で大量処理が必要な夜間バッチに最適。条件反射：「大量＋急がない＋コスト最優先」→ Batches API。
🇺🇸 English
A SaaS company is building a system to analyze support tickets using the Claude API. Up to 80,000 tickets arrive each night in bulk, and all must be categorized and prioritized by the next morning. Which API usage pattern best minimizes cost while meeting this requirement?
✓ Correct Answer
Use the Message Batches API. It provides up to 50% cost reduction compared to synchronous requests and guarantees responses within 24 hours. Each batch supports up to 100,000 requests or 256 MB, so all 80,000 tickets can be sent in a single batch. Results are retained for 29 days and matched via custom_id.

Q2Applications and Integration
🇯🇵 Japanese
EC サイトが Claude API に tool_use（Function Calling）を統合している。ユーザーが「在庫を確認して注文を完了して」と入力した場合、Claude は check_inventory ツールと place_order ツールを両方呼び出す必要がある。この 2 つのツール呼び出しを最も効率よく処理する方法はどれか？
✓ 正解
Claude が tool_use ブロックを複数同時に返した場合（parallel tool calls）、アプリ側は各ツールを並列実行し、すべての tool_result を一つの messages 配列にまとめて Claude に返す。ただし check_inventory の結果が place_order の入力に必要な場合は順次実行が必要。
💡 暗記ポイント
Claude API は 1 ターンで複数の tool_use を返せる（parallel tool calls）。依存関係がないツールは並列実行でレイテンシを削減できる。一方、前のツール結果が次のツールの引数になる場合は逐次実行が必要。依存関係の有無を設計段階で整理することが重要。
🇺🇸 English
An e-commerce site integrates Claude API with tool_use (Function Calling). When a user says 'Check inventory and complete the order,' Claude needs to call both check_inventory and place_order. What is the most efficient way to handle these two tool calls?
✓ Correct Answer
When Claude returns multiple tool_use blocks in a single turn (parallel tool calls), the application runs each tool in parallel and returns all tool_result blocks together in one messages array. However, if check_inventory output is required as input for place_order, sequential execution is necessary.

Q3Applications and Integration
🇯🇵 Japanese
リーガルテック企業が Claude API を使って契約書レビューアプリを開発中。ユーザーが 200 ページの PDF をアップロードすると、全文を Claude に送ると 200k トークンを超えコストと遅延が問題になる。最も効果的なアーキテクチャはどれか？
✓ 正解
PDF をセクション単位でチャンク分割し、関連性スコアリング（埋め込みベクトル検索）で質問に関連する上位チャンクのみを抽出して Claude に送る RAG（Retrieval-Augmented Generation）パターンを採用する。全文送付が必要な場合は Prompt Caching でコストを削減する。
💡 暗記ポイント
大規模ドキュメントの処理には RAG が有効。全文をコンテキストに詰め込む「Stuffing」はコスト・速度ともに非効率。関連チャンクのみ抽出することでトークン消費を 80〜90% 削減できる。頻繁に参照する長い文書には Prompt Caching（最大 90% 削減）も組み合わせると効果的。
🇺🇸 English
A legaltech company is building a contract review application using the Claude API. When a user uploads a 200-page PDF, sending the full text to Claude exceeds 200k tokens, causing cost and latency issues. What is the most effective architecture?
✓ Correct Answer
Adopt a RAG (Retrieval-Augmented Generation) pattern: chunk the PDF into sections, use relevance scoring (embedding vector search) to extract only the top chunks related to the query, and send only those to Claude. For cases where full-text access is required, use Prompt Caching to reduce costs.

🇯🇵 Japanese
ニュースアグリゲーターが Claude API を使ってリアルタイム要約をユーザーに提供している。長い記事（3,000 語）の要約が完了するまでユーザーが待たされ UX が悪い。最も適切な改善策はどれか？
✓ 正解
Streaming API（server-sent events）を使用し、Claude が生成したトークンをチャンクごとにリアルタイムでクライアントに送信する。ユーザーはページロード後すぐにテキストが流れるのを確認でき、体感速度が大幅に向上する。

✓ Correct Answer
Use the Streaming API (server-sent events) to send tokens to the client in real time as Claude generates them. Users see text appearing immediately after page load, dramatically improving perceived speed.

Q5Applications and Integration
🇯🇵 Japanese
モバイルアプリが Claude API に大量リクエストを送信しており、断続的に HTTP 529 (Overloaded) エラーが発生している。サービスの安定性を保ちながら全リクエストを確実に処理するための最善のエラー処理戦略はどれか？
✓ 正解
指数バックオフ（Exponential Backoff）にジッター（ランダム待機）を加えた再試行ロジックを実装する。初回リトライは 1 秒待機、以降は 2 秒・4 秒・8 秒と倍増させ、最大待機上限（例: 60 秒）を設ける。同時に x-ratelimit-remaining ヘッダーを監視してレート制限を事前に検知する。
💡 暗記ポイント
529 は一時的な過負荷エラーでリトライ有効（cf. 400/401 はリトライ不要）。ジッターなしの指数バックオフは「リトライの集中」を起こすため、ランダム待機を加えて分散させる。レート制限ヘッダー（x-ratelimit-remaining, x-ratelimit-reset）を監視して事前制御するのもベストプラクティス。
🇺🇸 English
A mobile app sending high volumes of requests to the Claude API is experiencing intermittent HTTP 529 (Overloaded) errors. What is the best error handling strategy to maintain service stability while ensuring all requests are processed?
✓ Correct Answer
Implement retry logic using exponential backoff with jitter: wait 1 second on the first retry, doubling to 2, 4, and 8 seconds, with a maximum cap (e.g., 60 seconds). Also monitor the x-ratelimit-remaining header to proactively detect rate limit exhaustion.

jitterジッターバックオフ待機時間にランダム要素を加えること。リトライの同期を防ぐ

🇯🇵 Japanese
金融レポート生成システムが Claude API を使っている。同じ 15,000 トークンの詳細な財務規制ガイドラインを、日々 5,000 件のレポート生成リクエストの system プロンプトに毎回含めている。このコスト構造を最も効率よく改善する方法はどれか？
✓ 正解
cache_control: {"type": "ephemeral"} を財務規制ガイドラインのコンテンツブロックに付与して Prompt Caching を有効化する。キャッシュヒット時のトークンコストは通常の 10% 程度に削減され、5 分間（TTL）保持される。5,000 件 × 15,000 トークンの繰り返し課金が大幅に削減される。
💡 暗記ポイント
Prompt Caching は同一プレフィックス（system プロンプトや長い文書）の再利用コストを最大 90% 削減する機能。cache_control フィールドで「ここまでキャッシュせよ」と境界を指定する。TTL はデフォルト 5 分（Sonnet 系は延長可）。頻繁に変化する動的コンテンツよりも、固定の長文コンテキストに最適。
🇺🇸 English
A financial report generation system uses the Claude API. The same 15,000-token detailed financial regulations guideline is included in the system prompt for 5,000 report generation requests per day. What is the most efficient way to improve this cost structure?
✓ Correct Answer
Enable Prompt Caching by adding cache_control: {"type": "ephemeral"} to the financial regulations content block. Cached tokens cost approximately 10% of normal input tokens and are retained for 5 minutes (TTL), dramatically reducing the repeated billing for 5,000 requests × 15,000 tokens.

Q7Applications and Integration
🇯🇵 Japanese
Webhook 通知システムを構築している。Claude API の非同期バッチ処理が完了したとき、外部の在庫管理システムに HTTP POST で結果を通知したい。セキュリティと信頼性の両方を確保するために必要な実装はどれか？
✓ 正解
Webhook エンドポイントで HMAC-SHA256 署名検証を実装する（ヘッダーの X-Signature と送信ボディのハッシュを照合）。また、冪等性キー（idempotency key）を用いて重複配信による二重処理を防ぎ、5xx エラー時はキュー（SQS など）への再エンキューで再送保証を実現する。
💡 暗記ポイント
Webhook は「サーバーがクライアントに」イベントを通知するプッシュ型の仕組み。セキュリティ確保には署名検証が必須（なりすまし防止）。信頼性確保には「少なくとも一度（at-least-once）」配信と冪等性設計が重要。配信失敗時の DLQ（Dead Letter Queue）設計も忘れずに。
🇺🇸 English
You are building a webhook notification system. When Claude API asynchronous batch processing completes, you need to notify an external inventory management system via HTTP POST. What implementation ensures both security and reliability?
✓ Correct Answer
Implement HMAC-SHA256 signature verification on the webhook endpoint (comparing the X-Signature header with a hash of the request body). Use idempotency keys to prevent duplicate processing from repeated deliveries, and guarantee redelivery by re-enqueuing failed requests (5xx errors) to a queue such as SQS.

HMAC-SHA256HMAC-SHA256署名秘密鍵とハッシュ関数でペイロードに署名し、送信元の正当性を検証する仕組み
idempotency key冪等性キー同一リクエストを複数回処理しても結果が変わらないことを保証するためのキー

Q8Model Selection and Optimization
🇯🇵 Japanese
スタートアップが AI チャットボットを構築している。ユーザー質問の 90% は「営業時間は？」「返品ポリシーは？」などのシンプルな FAQ で、残り 10% は複雑な注文トラブルの対応。コスト最適化のために最も適切なモデル選択戦略はどれか？
✓ 正解
ルーターエージェントパターンを採用する。まず軽量な分類ロジック（またはモデル自体）で質問の複雑さを判定し、シンプルな FAQ は Claude Haiku（高速・最低コスト）で処理、複雑なトラブル対応は Claude Sonnet（バランス型）にルーティングする。
💡 暗記ポイント
すべての質問を高性能・高コストモデルで処理するのは非効率。Haiku は簡単なタスクに対して Sonnet の 1/10 以下のコストで同等の品質を提供できる。ルーターパターンはコスト最適化の定番手法。分類は質問の長さ・キーワード・センチメントなどを基準にできる。
🇺🇸 English
A startup is building an AI chatbot. 90% of user questions are simple FAQs like 'What are your business hours?' or 'What is the return policy?', while the remaining 10% involve complex order issues. What is the most appropriate model selection strategy for cost optimization?
✓ Correct Answer
Adopt a router agent pattern: use lightweight classification logic (or the model itself) to assess question complexity, then route simple FAQs to Claude Haiku (fastest, lowest cost) and complex troubleshooting to Claude Sonnet (balanced performance).

🇯🇵 Japanese

✓ 正解
MCP サーバーは tools（SQLクエリ実行などのアクション）と resources（スキーマ定義や読み取り専用テーブルの静的データ）を定義する。セキュリティ設計として：① 読み取り専用クエリのみ許可（DDL/DML は禁止）、② クエリパラメータはバインド変数で SQL インジェクション防止、③ 接続情報は環境変数で管理、④ クエリ結果の行数上限を設ける。
💡 暗記ポイント
MCP はツール（actions）とリソース（data）を標準化されたインターフェースでClaudeに提供するプロトコル。MCPサーバーはデータソースへの安全なアクセスレイヤーとして機能する。Tools = Claude が呼び出せる関数 / Resources = Claude が参照できる静的データ / Prompts = 再利用可能なプロンプトテンプレート の 3 要素で構成される。
🇺🇸 English
A development team is building an MCP (Model Context Protocol) server to connect an internal PostgreSQL database to Claude. What types of capabilities should the MCP server provide, and what are the best practices for security design?
✓ Correct Answer
The MCP server should define tools (actions such as SQL query execution) and resources (static data like schema definitions or read-only tables). Security best practices: ① Allow only read-only queries (prohibit DDL/DML); ② Use bind variables for query parameters to prevent SQL injection; ③ Manage connection strings via environment variables; ④ Set a row limit on query results.

🇯🇵 Japanese
MCP サーバーを開発中。ファイルシステムへのアクセスを提供する際に、ファイルの読み取り（静的コンテンツ）と、ファイルの作成・削除（アクション実行）をそれぞれどのプリミティブ（tools / resources / prompts）に実装すべきか？
✓ 正解
ファイルの読み取り（静的コンテンツ参照）は resources として実装する（例: file:///path/to/file）。Claude がコンテキストに取り込む読み取り専用データとして提供される。ファイルの作成・削除などの副作用を伴うアクションは tools として実装する。tools はClaudeが実行を要求し、ユーザー確認を経て実行される。
💡 暗記ポイント
MCP の 3 プリミティブ：① Resources = 読み取り専用の静的データ提供（ファイル・DB レコード・設定）② Tools = 副作用を伴うアクション実行（ファイル作成・API 呼び出し・DB 書き込み）③ Prompts = 再利用可能なプロンプトテンプレート（ユーザーが選択して使う）。副作用の有無が tools と resources の分岐点。
🇺🇸 English
You are developing an MCP server providing filesystem access. Which MCP primitive (tools / resources / prompts) should file reading (static content) and file creation/deletion (action execution) each be implemented as?
✓ Correct Answer
File reading (static content reference) should be implemented as a resource (e.g., file:///path/to/file), provided as read-only data that Claude can incorporate into its context. File creation, deletion, and other operations with side effects should be implemented as tools. Tools are requested by Claude for execution and require user confirmation.
