Q001エージェント・ワークフロー正解: C
Your team needs to draft a weekly summary email from a fixed list of five metrics pulled from three internal APIs. The steps never change and the output format is fixed. A colleague suggests building a full agent with the Claude Agent SDK so it can 'figure out the best way to get the data.' What should you recommend instead?
チームは、3つの社内APIから取得した固定の5つの指標を使って、毎週の要約メールを作成する必要があります。手順は常に同じで、出力フォーマットも固定です。同僚が「データ取得の最善の方法を自分で判断できるように」Claude Agent SDK でフルのエージェントを構築することを提案しています。代わりに何を推奨すべきですか？
C ✅ 正解
Use a predefined workflow that calls the three APIs in a fixed sequence and formats the result with a fixed template.
3 つの API を固定の順序で呼び出し、結果を固定テンプレートで整形する、事前定義されたワークフローを使う。
解説
When a task is fully specified, repeatable, and doesn't require the model to decide what to do next, a predefined workflow (fixed code path) is simpler, cheaper, and more predictable than an agent. The general principle is to start with the simplest architecture that satisfies the requirement; agents add value only when the process can't be fully specified in advance.
タスクが完全に仕様化されており、繰り返し可能で、モデルが次に何をすべきか判断する必要がない場合、事前定義されたワークフロー（固定のコードパス）の方が、エージェントよりもシンプルで安価かつ予測可能です。一般原則として、要件を満たす最もシンプルなアーキテクチャから始めるべきであり、事前にプロセスを完全に仕様化できない場合にのみエージェントが価値を持ちます。

Q003エージェント・ワークフロー正解: A

単一エージェントのリサーチアシスタントが、「ソースを探す」ことと「最終レポートを書く」ことの両方を1つの長時間実行ループの中でうまく機能させ続けるのに苦労しています。ソースが蓄積するにつれて、執筆の質が低下していきます。ここで subagent を導入する主な利点は何ですか？

このシナリオにおける subagent の核心的な利点は、コンテキスト分離です。冗長なソース発見作業を別のコンテキストで行えるため、最終的な統合・執筆ステップで利用可能なコンテキストを圧迫しません。subagent はコーディネーターの履歴を自動的に継承せず、API 呼び出しを排除するわけでもなく、委任と通信を管理するコーディネーターは通常引き続き必要です。

Your application sends a Messages API request and receives back `stop_reason: "max_tokens"`. What does this indicate, and what is the appropriate response?
あなたのアプリケーションが Messages API にリクエストを送り、`stop_reason: "max_tokens"` を受け取りました。これは何を示しており、どのように対応するのが適切ですか？
A ✅ 正解
The output was cut off at the token limit before completing naturally; consider raising max_tokens for this request.
出力が自然に完了する前にトークン上限で打ち切られた。このリクエストの max_tokens を増やすことを検討すべきである。

`stop_reason` が `"max_tokens"` であることは、モデルが自然に完了する前に設定されたトークン上限に達したため、応答が打ち切られたことを意味します。これは、自然な完了を表す `"end_turn"`、ツール呼び出しを要求する `"tool_use"`、安全上の拒否を表す `"refusal"`、サーバーサイドツールが実行途中で一時停止したことを表す `"pause_turn"` とは異なります。
Q012アプリケーション・統合正解: B

B ✅ 正解
Streaming via Server-Sent Events, with content_block_delta events carrying the text between message_start and message_stop.

段階的でトークンごとの UI 更新には、ストリーミング（Server-Sent Events として配信される）が正しい機能であり、message_start、続いて content_block_start、繰り返される content_block_delta イベント（段階的なトークン）、content_block_stop、message_delta（stop_reason と usage を含む）、そして最後に message_stop という定義されたイベントの並びを発行します。

Your nightly job needs to process 20,000 support tickets to generate an internal quality report by 9am the next morning. There is no user waiting synchronously, and cost is the top priority. Which API approach best fits, and what must your code handle as a result?

D ✅ 正解
The Message Batches API, with each response correlated back to its request via the `custom_id` field.

Message Batches API は、まさにこの種の大量で遅延を許容できるコスト重視の夜間ワークロード向けに設計されており、同期呼び出しに比べて大幅なコスト割引を提供します。バッチの結果は元の順序で返ってくる保証がなく、処理に最大24時間かかる可能性があるため、アプリケーションは `custom_id` フィールドを使って各結果を元のリクエストに対応付けて追跡する必要があります。

`tool_choice` governs tool-calling behavior: `auto` (the default) lets the model decide, `any` forces some tool call, `none` forbids tools, and `{"type": "tool", "name": ...}` forces one specific tool — exactly what a must-always-extract endpoint needs. Return both `tool_result` blocks, each carrying its matching `tool_use_id`, together in one single user message.

For a new agent, a team plans to implement from scratch: (1) a generic web-search tool, (2) a generic file-editing tool, and (3) an action that submits orders to their proprietary internal ERP system. Applying the built-in-versus-custom tradeoff, which plan is right?

Use built-in tools for web search and file editing, and build a custom tool only for the proprietary ERP order-submission action.
Web 検索とファイル編集には組み込みツールを使い、独自性のある ERP への注文送信アクションのためだけにカスタムツールを構築する。
